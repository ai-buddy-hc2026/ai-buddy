# Черновик схемы БД AI-buddy

Статус: проект схемы для первой миграции; продуктовые решения ниже уточнены с владельцем задачи. Документ не является выполненной миграцией. Задача: [#5](https://github.com/ai-buddy-hc2026/ai-buddy/issues/5).

Целевая СУБД: PostgreSQL 16 с расширением `vector`, которое уже включено в Docker Compose. Этот документ не создаёт таблицы и не меняет данные. Миграции и seed относятся к отдельной задаче.

В текущей ветке в рамках #19 реализованы миграции `teams`, `users`,
`onboarding_plans`, `tasks`, `task_status_history` и автоматический seed
пользователей и чек-листа. Остальная схема остается целевой. Связи
`task_kb_documents` сохранены в seed/checklist.json, но их миграция и загрузка
зависят от реальных документов KB (#28, PR #56/#69). Это не реализация всей схемы.

Схема покрывает панель онбординга, чат с источниками, подтверждение действий, передачу вопроса наставнику, публикацию его ответа в базу знаний и события для метрик. Все данные MVP синтетические.

## 1. Принятые решения и границы

- Основные сущности из задачи: `users`, `teams`, `onboarding_plans`, `tasks`, `task_status_history`, `actions_log`, `chat_messages`, `escalations`, `kb_documents`, `kb_chunks`, `events`, `feature_flags`.
- Дополнительно нужны `conversations`, `chat_requests` и `task_kb_documents`. Они определяют владельца беседы, состояние одной генерации и связь задач с несколькими документами. История сообщений, состояние генерации и результаты инструментов имеют разные жизненные циклы.
- Пользователь принадлежит одной команде и имеет одну роль: `intern`, `buddy` или `lead`. Переводы между командами и история назначений за пределами MVP; `team_id` существующего пользователя не меняется автоматически.
- Один активный план на стажёра. Один наставник и один руководитель на пользователя, если назначены. Назначения хранятся явно, а не вычисляются по единственному пользователю с ролью в команде.
- Источником прикладных данных и истории служит PostgreSQL. Redis используется для транспорта и временных записей, но не заменяет историю и журнал действий.
- Контракт Go/Python находится в [PR #60](https://github.com/ai-buddy-hc2026/ai-buddy/pull/60/files). Для этой схемы зафиксированы UUID внутренних ID и обязательный `revision` источника. `revision` уже добавлен в контракт; уточнение UUID нужно перенести в его актуальную редакцию до интеграции. Это синхронизация принятого решения, а не повторное согласование формата ID.
- MVP использует mock-login с выбором тестового пользователя, без пароля и регистрации. Приглашения от куратора относятся к будущему развитию, описанному ниже.
- Эмбеддинги: `intfloat/multilingual-e5-base`, 768 измерений, PostgreSQL-тип `vector(768)`. LLM для серверного развёртывания вызывается через OpenAI API и не определяет размерность эмбеддингов.

## 2. Общие правила

| Правило | Решение |
|---------|---------|
| Идентификаторы | Сущности имеют `uuid`, PK `id`, создаваемый Go или `gen_random_uuid()`. Исключение: составной PK таблицы связей `task_kb_documents`. В HTTP/JSON внутренние ID передаются строками UUID. |
| Тестовые логины | `intern_anya`, `buddy_ilya` и подобные значения являются `users.login`. В `user_id`, `team_id`, `request_id`, `conversation_id`, `action_id`, `document_id` передаются UUID, а не логины или коды. Внешние номера интеграций вроде `ABS-1042` сохраняют свой формат. |
| Время | Моменты времени: `timestamptz`, запись и сравнение в UTC. Календарные даты: `date`. Часовой пояс хранится отдельно как имя IANA. |
| Обязательность | Все поля в таблицах ниже имеют `NOT NULL`, кроме явно помеченных `NULL`. |
| Создание | Во всех таблицах есть `created_at timestamptz NOT NULL DEFAULT now()`. В списках полей ниже он опущен. |
| Изменение | Изменяемые таблицы имеют `updated_at timestamptz NOT NULL DEFAULT now()`. Его обновляет репозиторий Go при каждом изменении; одного `DEFAULT` недостаточно. |
| Строки | Строки без явно разрешённого пустого значения проверяются на непустое значение после `btrim`. `DEFAULT ''` разрешает пустую строку. Лимиты API проверяются также до записи. |
| Статусы | `text` с `CHECK` на перечисленные значения. Отдельные PostgreSQL enum в первом варианте не нужны. |
| JSON | `jsonb` используется для снимков и расширяемых параметров, но не вместо FK, владельца, команды, статуса или ключа идемпотентности. Тип объекта/массива проверяется через `jsonb_typeof`. |
| Удаление | Ссылки по умолчанию `ON DELETE RESTRICT`, а сущности архивируются или деактивируются. Каскадное удаление допускается только для производных `kb_chunks` при явном удалении документа. |
| Индексы | PK и `UNIQUE` уже создают индексы. Для FK и списочных запросов ниже указаны дополнительные индексы; одинаковые индексы не дублируются. |

### 2.1. Разделение данных команд

Для сущностей с `team_id`, на которые ссылаются через составной FK, нужен дополнительный `UNIQUE (id, team_id)`: `users`, `onboarding_plans`, `tasks`, `conversations`, `chat_requests`, `actions_log`, `escalations`, `kb_documents`. `team_id` этих сущностей ссылается на `teams.id`.

Ссылка вида `FK (user_id, team_id) -> users (id, team_id)` исключает связь с пользователем другой команды. Для nullable-ссылок используется стандартный `MATCH SIMPLE`: при `NULL` в идентификаторе связи нет, а отдельный обязательный `team_id` продолжает ссылаться на команду.

У дочерних записей без собственного `team_id` область доступа выводится через обязательного родителя: история статуса через задачу, сообщение через запрос генерации. Запросы к таким таблицам обязательно включают соответствующий JOIN и проверку доступа.

Составные FK защищают целостность данных, но не заменяют авторизацию. Go проверяет активность пользователя, роль, владельца и назначение наставника перед каждой операцией. Произвольный `team_id` из браузера или аргументов агента не определяет права.

### 2.2. Что обеспечивает БД, а что Go

В БД фиксируются FK, уникальность, допустимые значения и локальные условия строки. Роль наставника, допустимость перехода статуса, актуальное назначение, права на инструмент и согласованность нескольких сущностей проверяются Go в транзакции.

Не следует реализовывать межтабличные правила через `CHECK` с обращением к другим строкам. Для них нужны FK, транзакционная логика или отдельно обоснованный триггер. См. [ограничения PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-constraints.html).

## 3. Таблицы

### 3.1. `teams`

Команда и настройки по умолчанию.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `code` | `text` | Уникальный стабильный код для seed, например `team_avito_ai`. |
| `name` | `text` | Название. |
| `timezone` | `text` | IANA timezone, например `Europe/Moscow`. Валидирует Go. |
| `active` | `boolean DEFAULT true` | Команда доступна для новых операций. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: `UNIQUE (code)`. Руководитель назначается через `users.manager_id`; роль `lead` сама по себе не означает единственность в команде.

### 3.2. `users`

Тестовые пользователи и назначения.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | Команда. |
| `login` | `text` | Уникальный нормализованный тестовый логин. |
| `display_name` | `text` | Имя для интерфейса. |
| `role` | `text` | `intern`, `buddy`, `lead`. |
| `buddy_id` | `uuid NULL` | Назначенный наставник. |
| `manager_id` | `uuid NULL` | Назначенный руководитель. |
| `timezone` | `text NULL` | Настройка пользователя; при `NULL` используется timezone команды. |
| `active` | `boolean DEFAULT true` | Можно ли входить и выполнять операции. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: `UNIQUE (login)`; `CHECK (login = lower(btrim(login)))`; составные FK `(buddy_id, team_id)` и `(manager_id, team_id)` на `users`; запрет `buddy_id = id` и `manager_id = id` при непустых назначениях. Go проверяет, что назначены активные пользователи с допустимыми ролями и не создаётся цикл руководителей.

Индексы: `(team_id, role)`, `(buddy_id) WHERE buddy_id IS NOT NULL`, `(manager_id) WHERE manager_id IS NOT NULL`.

Пароли, ключи LLM и JWT в таблице не хранятся: MVP использует mock-login. JWT содержит идентификатор, а актуальные права проверяются Go.

Вход выполняется выбором тестового пользователя: Go находит активную запись, выдаёт JWT и проверяет права при дальнейших операциях. Это имитация входа для демонстрации, а не полноценная проверка личности. Поля `password`, `password_hash`, таблицы приглашений и самостоятельная регистрация в MVP не добавляются.

Архитектурное развитие авторизации: после MVP куратор сможет приглашать пользователей с привязкой к команде и допустимой роли. В roadmap эта работа включает принятие приглашения, срок его действия, защиту от повторного использования и выбор реального способа входа. Локальные учётные данные либо внешний провайдер идентификации выбираются при реализации этой фичи; приглашение само по себе не определяет способ хранения паролей. Роль куратора и новые таблицы не добавляются в текущую схему заранее.

### 3.3. `onboarding_plans`

Персональный экземпляр плана, а не общий шаблон чек-листа.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | Команда стажёра. |
| `intern_id` | `uuid` | Владелец плана. |
| `title` | `text` | Название плана. |
| `start_date` | `date` | Начало адаптации; в seed приходится на понедельник. Ограничения на день недели для остальных планов нет. |
| `current_stage` | `text` | `week_1`, `week_2`, `weeks_3_4`. |
| `status` | `text DEFAULT 'active'` | `active`, `completed`, `archived`. |
| `completed_at` | `timestamptz NULL` | Факт завершения, сохраняется при архивировании. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: FK `(intern_id, team_id) -> users`; частичный `UNIQUE (intern_id) WHERE status = 'active'`; при `status = 'completed'` обязателен `completed_at`, при `active` он пуст. Go проверяет роль владельца `intern`.

Индекс: `(intern_id, created_at DESC, id)`. Прогресс и следующий шаг вычисляются по задачам, отдельный процент в БД не хранится. Правило смены этапа и его связь с датами/задачами согласуются с чек-листом; БД не меняет этап автоматически.

Прогресс относится к единому плану стажёра. Страница наставника показывает задачи того же плана, а не их копии; просмотр со стороны наставника не создаёт второй прогресс или второе подтверждение результата.

### 3.4. `tasks`

Задачи экземпляра плана, в том числе задачи наставника.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | Команда плана. |
| `plan_id` | `uuid` | Родительский план. |
| `assignee_id` | `uuid` | Один назначенный ответственный: выполняет задачу и подтверждает результат. Роль определяется задачей чек-листа. |
| `seed_key` | `text` | Стабильный ключ задачи в seed; сохраняется после редактирования названия. |
| `stage` | `text` | `week_1`, `week_2`, `weeks_3_4`. |
| `title` | `text` | Название. |
| `description` | `text DEFAULT ''` | Описание. |
| `position` | `integer` | Порядок внутри этапа, `>= 0`. |
| `due_date` | `date NULL` | Календарный дедлайн, рассчитанный от `start_date` по правилам ниже. Дни могут попадать на выходные. |
| `status` | `text DEFAULT 'todo'` | `todo`, `in_progress`, `blocked`, `done`. |
| `version` | `integer DEFAULT 1` | Версия для конкурентного изменения, `>= 1`. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: FK `(plan_id, team_id) -> onboarding_plans`, `(assignee_id, team_id) -> users`; `UNIQUE (plan_id, seed_key)`; `UNIQUE (plan_id, stage, position)`.

Индекс: `(assignee_id, status, due_date, id)`. Индекс уникальности `(plan_id, stage, position)` обслуживает получение плана. Стажёр меняет только свои разрешённые задачи, а наставник работает в пределах назначенных ему стажёров; одного совпадения команды недостаточно. Документы связываются через `task_kb_documents`, одиночного поля документа в `tasks` нет.

Для задачи «Организовать работу с наставником» `assignee_id` указывает на стажёра. Задача входит в его план и прогресс, он подтверждает результат. Назначенный наставник видит её на своей странице вместе с остальными задачами этого стажёра. Вторая задача, второй исполнитель в этой строке и отдельное подтверждение наставника не создаются. У других задач остаются ответственные из чек-листа.

Правила календарных дедлайнов:

- День старта считается днём 1. Срок «день N» означает `start_date + (N - 1)` календарных дней, включая выходные; отдельный производственный календарь в MVP не используется.
- Если старт приходится на понедельник, вторник или среду, конец первой недели - ближайшая пятница.
- Если старт приходится на четверг, пятницу, субботу или воскресенье, конец первой недели - пятница следующей календарной недели. При старте в пятницу дедлайн не приходится на день старта.
- Конец недели N - первая определённая выше пятница плюс `7 * (N - 1)` календарных дней. Начало отсчёта остаётся исходным `start_date`.
- Дедлайн действует до конца указанной даты в часовом поясе плана: в MVP используется часовой пояс его команды. В БД остаётся `date`, а не искусственное время `23:59:59` в UTC. Часовой пояс команды с активным планом не меняется без отдельного решения.
- Все планы синтетических стажёров в seed начинают стажировку в понедельник. Это правило seed, а не `CHECK` на `onboarding_plans.start_date`.

| Пример старта | День старта | Конец 1-й недели | Конец 2-й недели |
|----------------|-------------|------------------|------------------|
| 2026-11-09 | Понедельник | 2026-11-13 | 2026-11-20 |
| 2026-11-10 | Вторник | 2026-11-13 | 2026-11-20 |
| 2026-11-11 | Среда | 2026-11-13 | 2026-11-20 |
| 2026-11-12 | Четверг | 2026-11-20 | 2026-11-27 |
| 2026-11-13 | Пятница | 2026-11-20 | 2026-11-27 |
| 2026-11-14 | Суббота | 2026-11-20 | 2026-11-27 |
| 2026-11-15 | Воскресенье | 2026-11-20 | 2026-11-27 |

Обозначения «рабочий день» в исходном чек-листе нужно синхронизировать с принятым здесь календарным отсчётом при подготовке seed. Эти правила определяют дедлайны; критерий перехода `current_stage` остаётся отдельным правилом прикладного слоя.

### 3.5. `task_kb_documents` (дополнительная)

Связь многие-ко-многим: задача может иметь несколько документов, документ может использоваться в нескольких задачах. Ноль связанных документов тоже допустим.

| Поле | Тип | Назначение |
|------|-----|------------|
| `task_id` | `uuid` | Связанная задача. Часть составного PK. |
| `document_id` | `uuid` | Документ KB. Часть составного PK. |
| `team_id` | `uuid` | Общая команда задачи и документа, FK на `teams.id`. |
| `position` | `integer` | Порядок материалов в задаче, `>= 0`. |
| `updated_at` | `timestamptz` | Последнее изменение связи/порядка. |

Ограничения: `PRIMARY KEY (task_id, document_id)`; `UNIQUE (task_id, position)`; FK `(task_id, team_id) -> tasks (id, team_id)` и `(document_id, team_id) -> kb_documents (id, team_id)`. Составные FK исключают привязку документа другой команды. Собственного `id` у связи нет; общий `created_at` сохраняется.

Обратный индекс: `(document_id, task_id)`. PK обслуживает проверку пары, уникальный индекс позиции - вывод материалов задачи по порядку. Ссылки по умолчанию `ON DELETE RESTRICT`; архивирование документа не удаляет связь. Go проверяет права на задачу и документ при изменении связи и на чтении материала.

### 3.6. `task_status_history`

Неизменяемая история переходов статуса.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `task_id` | `uuid` | FK на `tasks.id`. |
| `version` | `integer` | Версия задачи после перехода, `>= 1`. |
| `from_status` | `text NULL` | Предыдущий статус; `NULL` только для создания. |
| `to_status` | `text` | Новый статус из списка статусов задач. |
| `changed_by` | `uuid NULL` | FK на `users.id`; `NULL` для системного создания. |
| `reason` | `text DEFAULT ''` | Краткое пояснение без секретов. |

Ограничения: `UNIQUE (task_id, version)`; `from_status IS NULL` только при `version = 1`, иначе статус задан и отличается от `to_status`. История и изменение задачи записываются одной транзакцией. Команда автора и его права проверяются через задачу в Go.

Отдельный индекс не нужен: `(task_id, version)` обслуживает историю. Переход в тот же статус считается повтором без новой строки истории и нового события метрик.

### 3.7. `conversations` (дополнительная)

Владелец и область доступа к беседе.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK; `conversation_id` контракта. |
| `team_id` | `uuid` | Команда владельца. |
| `owner_id` | `uuid` | Владелец беседы. |
| `title` | `text DEFAULT ''` | Необязательное название. |
| `status` | `text DEFAULT 'active'` | `active`, `archived`. |
| `updated_at` | `timestamptz` | Последняя активность/изменение. |

Ограничения: FK `(owner_id, team_id) -> users`; дополнительно `UNIQUE (id, owner_id, team_id)` для связи запросов с владельцем.

Индекс: `(owner_id, updated_at DESC, id)`. Наставник не получает доступ ко всем беседам команды. Контекст эскалации передаётся отдельным ограниченным снимком.

### 3.8. `chat_requests` (дополнительная)

Долговечное состояние одной генерации. Токены Pub/Sub здесь не хранятся.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK; `request_id` контракта. |
| `team_id` | `uuid` | Команда беседы. |
| `conversation_id` | `uuid` | Беседа. |
| `user_id` | `uuid` | Автор запроса. |
| `status` | `text DEFAULT 'running'` | `running`, `done`, `error`. |
| `context_snapshot` | `jsonb` | Объект: фактически переданные role, stage, timezone, timestamp. Не источник прав. |
| `input_hash` | `text` | SHA-256 канонического валидированного тела HTTP-запроса Python, не исходных байтов JSON. |
| `deadline_at` | `timestamptz` | Общий дедлайн генерации. |
| `last_seq` | `integer DEFAULT 0` | Номер последнего долговечно обработанного события, `>= 0`. |
| `terminal_seq` | `integer NULL` | Номер итогового `done`/`error`, `> 0`. |
| `error_code` | `text NULL` | Машинный код терминальной ошибки. |
| `error_message` | `text NULL` | Безопасное сообщение пользователю. |
| `finished_at` | `timestamptz NULL` | Завершение генерации. |
| `updated_at` | `timestamptz` | Последнее изменение состояния. |

Ограничения: FK `(conversation_id, user_id, team_id) -> conversations (id, owner_id, team_id)`; `deadline_at > created_at`; частичный `UNIQUE (conversation_id) WHERE status = 'running'`. При `running` поля завершения и ошибки пусты; при `done` заданы `finished_at`, `terminal_seq`, ошибки пусты; при `error` заданы все поля завершения и непустые код/сообщение. Для терминальной строки `last_seq = terminal_seq`.

Индексы: `(conversation_id, created_at, id)`, `(deadline_at) WHERE status = 'running'`. Пара `(created_at, id)` задаёт стабильный порядок запросов беседы.

`last_seq` фиксируется при сохранении предложения или терминального состояния, а не на каждом токене. Полный временный поток и его оперативный счётчик находятся в буфере Go. После потери буфера незавершённый запрос завершается ошибкой; продолжение с `last_seq` из БД не обещается. Redis-регистрация принятого запроса Python для защиты от повторного запуска хранится отдельно по правилам контракта.

Для воспроизведения терминального запроса используются финальное сообщение, ошибка и сохранённые предложения с их номерами. Если Go не смог записать ошибку из-за недоступности БД, фоновое восстановление после её возвращения переводит просроченный `running` в `error`.

### 3.9. `chat_messages`

Сообщение пользователя и успешно завершённый ответ assistant.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `request_id` | `uuid` | FK на `chat_requests.id`. |
| `role` | `text` | `user`, `assistant`. |
| `content` | `text` | Полный текст сообщения. |
| `sources` | `jsonb DEFAULT '[]'` | Массив снимков источников. |

Ограничения: `UNIQUE (request_id, role)`; непустой `content` для `user`; не более 4 000 символов для `user`, 20 000 для `assistant`; для `user` `sources = '[]'::jsonb`. Для `assistant` допустим пустой массив источников. Пустой текст assistant допустим только при наличии сохранённого предложения действия в этом запросе; это межтабличное условие проверяет Go при завершении. Число символов в PostgreSQL проверяется через `char_length`.

Команда, беседа и автор пользовательского сообщения определяются через `chat_requests`, без дублирования этих полей. Сообщение `user` создаётся вместе с запросом. Сообщение `assistant` создаётся только при успешном `done` в одной транзакции с терминальным состоянием. Частичный текст при ошибке не добавляется как полноценный ответ и не включается в history.

Формат элемента `sources`: `document_id` как строка UUID, строковые `title`, `section`, `url`, обязательный `revision` как целое `>= 1`. Редакция и метаданные берутся из найденного RAG-материала и передаются Python вместе с ответом. Если документ обновился во время генерации, Go сохраняет исходную редакцию, а не читает и подставляет текущую. Отсутствующий `revision` не заменяется на 1 и не принимается как корректный источник.

Это снимок цитирования; идентификатор внутри JSON не является FK. Go проверяет структуру и доступность источника перед сохранением, а открытие ссылки повторно проверяет права. Сам номер редакции не сохраняет старый текст и не гарантирует его просмотр: полная история текстов KB в MVP не добавляется. Архивирование документа не переписывает старый ответ, текущая версия по URL не выдаётся за точную копию процитированного материала.

История для LLM строится из завершённых запросов: не более 10 сообщений и 20 000 символов, с сохранением целых пар. Текущее сообщение передаётся отдельно.

### 3.10. `actions_log`

Сохранённое предложение действия, его подтверждение и результат. Таблица изменяемая; неизменяемые события переходов записываются в `events`.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK; `action_id` для подтверждения. |
| `team_id` | `uuid` | Область действия. |
| `request_id` | `uuid` | Генерация, предложившая действие. |
| `proposal_seq` | `integer` | Номер события `action_proposal`, `> 0`. |
| `actor_id` | `uuid` | Пользователь, для которого предложено действие. |
| `action_type` | `text` | Имя инструмента, например `absences.create_request`. Allowlist проверяет Go. |
| `parameters` | `jsonb` | Проверенные параметры как объект, включая доверенного согласующего. |
| `status` | `text DEFAULT 'proposed'` | `proposed`, `confirmed`, `executing`, `succeeded`, `failed`, `cancelled`. |
| `idempotency_key` | `uuid` | Устойчивый ключ выполнения, создаётся Go один раз. |
| `confirmed_by` | `uuid NULL` | Кто подтвердил действие. |
| `confirmed_at` | `timestamptz NULL` | Момент подтверждения. |
| `started_at` | `timestamptz NULL` | Начало выполнения. |
| `finished_at` | `timestamptz NULL` | Последнее завершение выполнения/отмена. |
| `attempt_count` | `integer DEFAULT 0` | Число попыток выполнения, `>= 0`. |
| `result` | `jsonb DEFAULT '{}'` | Объект результата, например ID `ABS-1042` и `pending_approval`. |
| `last_error` | `jsonb NULL` | Объект безопасной ошибки последней неуспешной попытки. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: FK `(request_id, team_id) -> chat_requests`, `(actor_id, team_id) -> users`, `(confirmed_by, team_id) -> users`; `UNIQUE (request_id, proposal_seq)`; `UNIQUE (idempotency_key)`. Go проверяет `actor_id = chat_requests.user_id`. Пара `confirmed_by`/`confirmed_at` либо целиком пуста, либо целиком задана. При `proposed` нет подтверждения и времени выполнения; при `confirmed`, `executing`, `succeeded`, `failed` подтверждение обязательно. Для `executing`, `succeeded`, `failed` нужен `started_at` и `attempt_count >= 1`. Для `succeeded`, `failed`, `cancelled` нужен `finished_at`, для остальных он пуст. `failed` требует `last_error`, а `succeeded` требует его очистки. При `confirmed` и `cancelled` `started_at` пуст. Отмена в MVP допускается до выполнения и не означает отмену уже отправленной заявки во внешнем сервисе.

Индексы: `(actor_id, created_at DESC, id)`, `(team_id, status, created_at, id)`. Частичный индекс на `status = 'executing'` добавляется, когда появится обработчик восстановления таких действий.

`succeeded` означает, что инструмент выполнил операцию, а не что руководитель одобрил отгул. Корпоративный статус, например `pending_approval`, находится в `result`. Повтор успешного подтверждения возвращает сохранённый результат; повтор неуспешной попытки использует тот же `idempotency_key`, увеличивает `attempt_count` и очищает `finished_at` при новом переходе в `executing`.

### 3.11. `escalations`

Переданный наставнику вопрос с ограниченным снимком контекста.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | Команда. |
| `action_id` | `uuid` | Подтверждённое действие `escalation.create`. |
| `intern_id` | `uuid` | Кто задал вопрос. |
| `buddy_id` | `uuid` | Назначенный получатель. |
| `question` | `text` | Переданный вопрос. |
| `context_snapshot` | `jsonb` | Массив разрешённых сообщений и идентификаторов источников, до 10 сообщений. |
| `status` | `text DEFAULT 'open'` | `open`, `answered`, `closed`. |
| `answer_text` | `text NULL` | Ответ наставника. |
| `answered_by` | `uuid NULL` | Автор ответа. |
| `answered_at` | `timestamptz NULL` | Момент ответа. |
| `closed_at` | `timestamptz NULL` | Закрытие. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: `UNIQUE (action_id)`; FK `(action_id, team_id) -> actions_log` и пользовательские FK `(intern_id, team_id)`, `(buddy_id, team_id)`, `(answered_by, team_id) -> users`. Go проверяет тип и подтверждение действия, его владельца и актуальное назначение наставника. Снимок не даёт наставнику доступа ко всей беседе.

Поля ответа либо все пусты, либо все заполнены, `answer_text` непуст. При `open` ответа и `closed_at` нет; при `answered` ответ есть, `closed_at` нет; при `closed` задан `closed_at`, ответ может отсутствовать. Публикация в KB определяется ссылкой из `kb_documents`, отдельный дублирующий boolean не нужен.

Индексы: `(buddy_id, status, created_at, id)`, `(intern_id, created_at DESC, id)`.

### 3.12. `kb_documents`

Текущая редакция документа базы знаний. Для MVP документ принадлежит одной команде; общие seed-документы загружаются отдельно для каждой команды со своим ID.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | Команда, которой доступен документ. |
| `slug` | `text` | Стабильный ключ/путь документа внутри команды. |
| `title` | `text` | Заголовок. |
| `content` | `text` | Markdown с пометкой о тестовой инструкции. |
| `source_type` | `text` | `seed`, `buddy_answer`. |
| `source_escalation_id` | `uuid NULL` | Источник ответа наставника. |
| `created_by` | `uuid NULL` | Автор публикации; `NULL` для seed. |
| `revision` | `integer DEFAULT 1` | Редакция контента, `>= 1`. |
| `status` | `text DEFAULT 'draft'` | `draft`, `published`, `archived`. |
| `index_status` | `text DEFAULT 'pending'` | `pending`, `ready`, `failed`. |
| `indexed_revision` | `integer NULL` | Успешно проиндексированная редакция. |
| `index_error` | `text NULL` | Безопасная причина ошибки индексации. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Ограничения: `UNIQUE (team_id, slug)`; `UNIQUE (source_escalation_id)`; FK `(source_escalation_id, team_id) -> escalations` и `(created_by, team_id) -> users`. Для `seed` источник эскалации пуст; для `buddy_answer` он и `created_by` обязательны. `indexed_revision` при наличии находится между 1 и `revision`; при `ready` равен `revision`; при `failed` обязателен `index_error`. Go проверяет наличие ответа наставника и разрешение на его публикацию.

Индекс: `(team_id, status, index_status)`. Текстовая плашка «Тестовая инструкция, не регламент Авито» проверяется при загрузке/публикации; её наличие не подменяет проверку прав.

Повтор публикации одного ответа на эскалацию возвращает существующий документ. Редактирование ответа не меняет опубликованный документ молча: новая редакция KB публикуется явно и повторно индексируется. Полная история редакций документов за пределами MVP; снимки цитирования в чате сохраняются независимо.

### 3.13. `kb_chunks`

Чанки и эмбеддинги конкретной редакции документа.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | Команда документа, обязательный фильтр RAG. |
| `document_id` | `uuid` | Родительский документ. |
| `document_revision` | `integer` | Редакция контента, `>= 1`. |
| `chunk_index` | `integer` | Порядок чанка, `>= 0`. |
| `section` | `text DEFAULT ''` | Раздел документа. |
| `content` | `text` | Текст для поиска и цитирования. |
| `content_hash` | `text` | SHA-256 текста для проверки повторной загрузки. |
| `embedding_model` | `text` | Идентификатор профиля модели: `intfloat/multilingual-e5-base` с зафиксированной ревизией весов. |
| `embedding` | `vector(768)` | 768-мерный нормализованный эмбеддинг; не `NULL`. |

Ограничения: FK `(document_id, team_id) -> kb_documents (id, team_id) ON DELETE CASCADE`; `UNIQUE (document_id, document_revision, chunk_index)`. Одновременно используется одна выбранная модель эмбеддингов; смена модели требует переиндексации, а не сравнения векторов разных моделей.

Индекс: `(team_id, embedding_model, document_id, document_revision)`. Заголовок документа возвращается через JOIN с `kb_documents`, а не копируется во все чанки. Нельзя смешивать metadata разных редакций.

Выбрана `intfloat/multilingual-e5-base` с размерностью 768. При подготовке эмбеддингов используются `query: ` для вопроса и `passage: ` для текста документа, включая русский текст; векторы нормализуются по L2. Длина входа с префиксом и специальными токенами не превышает 512 токенов: чанкирование должно учитывать лимит, а не молча терять хвост материала. Основание: [карточка модели E5](https://huggingface.co/intfloat/multilingual-e5-base).

Для поиска принимается cosine distance, оператор pgvector `<=>`: меньшее расстояние означает более близкий результат. Если API поиска возвращает similarity, используется `1 - distance`; порог и направление сравнения должны соответствовать именно этой шкале, без умножения на 100 из демонстрационных примеров модели. Нулевые векторы и нечисловые/бесконечные компоненты отклоняются при индексации и подготовке запроса.

Для небольшого MVP используется точный поиск с фильтром команды, профиля модели, текущей редакции и опубликованного документа в состоянии `ready`. Идентификатор `embedding_model` включает зафиксированную ревизию весов, например `<model_id>@<commit_sha>`; он одинаков для запросов и чанков. Смена весов или правил подготовки текста требует нового профиля и переиндексации, даже при прежней размерности. Top-k и порог настраиваются по тестовым вопросам с Саматом; они не блокируют создание `vector(768)` в миграции. HNSW/IVFFlat пока не нужны; при добавлении индекс должен соответствовать cosine distance. Возможности и ограничения: [pgvector](https://github.com/pgvector/pgvector).

Для генерации ответов при развёртывании на своём сервере используется OpenAI API. Конкретная LLM и её ключ задаются конфигурацией AI-service, не колонками этой таблицы. Ключи и строки подключения не сохраняются в KB. OpenAI API не заменяет выбранную модель эмбеддингов и не меняет 768-мерный тип вектора.

### 3.14. `events`

Неизменяемые прикладные события для метрик и аудита отказов. Это не архив каждого токена LLM.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `team_id` | `uuid` | FK на `teams.id`, область события. |
| `actor_id` | `uuid NULL` | Пользователь-инициатор; `NULL` для системного события. |
| `request_id` | `uuid NULL` | Связанная генерация. |
| `action_id` | `uuid NULL` | Связанное действие. |
| `task_id` | `uuid NULL` | Связанная задача. |
| `event_type` | `text` | Код события по каталогу аналитики. |
| `schema_version` | `smallint DEFAULT 1` | Версия payload, `>= 1`. |
| `dedup_key` | `text NULL` | Уникальный ключ события при необходимости защиты от повторов. |
| `payload` | `jsonb DEFAULT '{}'` | Объект с разрешёнными полями метрик. |

Ограничения: `UNIQUE (dedup_key)`; составные FK с `team_id` к `users`, `chat_requests`, `actions_log`, `tasks` для соответствующих непустых идентификаторов. Источник события с неподтверждённым чужим ID не записывается как FK: попытка доступа фиксируется в области инициатора с безопасным описанием отказа.

Индексы: `(team_id, event_type, created_at, id)`, `(actor_id, created_at, id) WHERE actor_id IS NOT NULL`, `(request_id) WHERE request_id IS NOT NULL`, `(action_id) WHERE action_id IS NOT NULL`, `(task_id) WHERE task_id IS NOT NULL`.

Начальный каталог: `chat_question`, `answer_completed`, `answer_with_source`, `answer_unknown`, `action_proposed`, `action_confirmed`, `action_failed`, `escalation_created`, `policy_denied`, `task_status_changed`. События могут пересекаться: один ответ даёт `answer_completed` и при наличии источника `answer_with_source`. `answer_unknown` записывается по явному исходу «ответ не найден», а не просто по пустому массиву источников.

Каталог, поля и формулы метрик согласуются с аналитиком; это не PostgreSQL enum. Полный текст чата, токены доступа и параметры с секретами в `payload` не дублируются. Событие, связанное с изменением БД, записывается в той же транзакции. Пример `dedup_key`: `request:<uuid>:answer_completed` или `task:<uuid>:version:<n>:status_changed`.

### 3.15. `feature_flags`

Runtime-флаги по приложению, команде и пользователю.

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | `uuid` | PK. |
| `flag_key` | `text` | Стабильное имя флага. |
| `team_id` | `uuid NULL` | FK на команду; `NULL` для глобального значения. |
| `user_id` | `uuid NULL` | Пользовательское переопределение. |
| `enabled` | `boolean` | Значение флага. |
| `description` | `text DEFAULT ''` | Назначение. |
| `updated_by` | `uuid NULL` | FK на `users.id`, автор изменения; `NULL` для seed/оператора. |
| `updated_at` | `timestamptz` | Последнее изменение. |

Области: оба ID пусты для глобального значения; только `team_id` заполнен для команды; оба заполнены для пользователя. `CHECK (user_id IS NULL OR team_id IS NOT NULL)` и FK `(user_id, team_id) -> users` не допускают пользовательский флаг без команды.

Уникальность: `UNIQUE NULLS NOT DISTINCT (flag_key, team_id, user_id)`, чтобы `NULL` не позволял создавать несколько глобальных или командных значений. PostgreSQL 16 поддерживает такую семантику [уникальных ограничений](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS).

Приоритет: пользовательское значение, затем командное, затем глобальное, затем документированное значение по умолчанию в Go. Явное отключение соответствующего сценария через env имеет приоритет над БД. Флаг не выдаёт дополнительных прав. Глобальные флаги управляются конфигурацией/seed; публичный интерфейс администрирования флагов в MVP не нужен.

Возможные ключи: `chat_enabled`, `absences_enabled`, `escalations_enabled`, `kb_publish_enabled`. Итоговый список и значения seed согласуются с владельцами сценариев.

## 5. Транзакции и конкурентные операции

### Изменение задачи

Go проверяет доступ и ожидаемую `version`, блокирует или условно обновляет строку задачи, увеличивает версию, добавляет `task_status_history` и `task_status_changed` одной транзакцией. Несовпадение версии возвращает конфликт без перезаписи чужого изменения. Создание задачи сразу добавляет историю версии 1. Повтор без изменения статуса не увеличивает прогресс повторно.

### Начало и завершение генерации

Создание `chat_requests`, сообщения user и `chat_question` атомарно. Частичный уникальный индекс закрывает гонку двух запусков одной беседы. HTTP-вызов Python выполняется после коммита и подтверждения Redis-подписки, без открытой транзакции БД на время LLM-вызова.

При `done` Go условно переводит `running -> done`, сохраняет assistant, источники, `terminal_seq` и события аналитики одной транзакцией. При ошибке аналогично сохраняет `running -> error`. Если другое завершение уже победило, позднее событие игнорируется. Закрытие SSE не меняет статус генерации.

Состояние `running` после падения Go восстанавливается как ошибка при потере буфера или истечении дедлайна, а не остаётся вечной блокировкой беседы. Гарантии восстановления полного token-потока не заявляются.

### Подтверждение действия

Предложение и `action_proposed` записываются до выдачи карточки в UI. Подтверждение блокирует действие, повторно проверяет пользователя и параметры, атомарно фиксирует подтверждение/событие и резервирует выполнение. Параллельный обработчик не выполняет уже занятое действие повторно.

Внешний вызов не удерживает долгую транзакцию БД. Его результат записывается отдельной транзакцией с условным переходом состояния. Если процесс упал после внешнего эффекта и до записи результата, состояние считается неопределённым: восстановление использует тот же `idempotency_key` и проверяет результат у интеграции. Один `UNIQUE` в PostgreSQL не обеспечивает однократное выполнение внешнего эффекта; мок/интеграция также должны поддерживать этот ключ.

Ключи не заменяются при техническом повторе, `succeeded` не переводится обратно в `proposed`. События подтверждения и отказа не дублируются при повторе одного перехода. Локальный мок эскалации создаёт `escalations`, результат действия и `escalation_created` одной транзакцией.

### Публикация ответа и индексация KB

Публикация проверяет доступ к эскалации и авторство ответа, создаёт или явно обновляет документ, увеличивает `revision` при изменении контента и выставляет `index_status = 'pending'`. Уникальность источника предотвращает дубли от повторного нажатия.

Эмбеддинги вычисляются вне транзакции БД. Чанки новой редакции вставляются атомарно с проверкой, что `revision` не изменилась; после успешной вставки документ получает `indexed_revision = revision` и `index_status = 'ready'`. При устаревшей редакции результат отбрасывается. При ошибке индексации документ остаётся недоступным для RAG, повтор не создаёт дубли чанков. Старые чанки удаляются после успешной замены в той же транзакции либо отдельной контролируемой очисткой.

Права и фильтр команды применяются до выдачи найденных чанков в модель. Запрос RAG учитывает `published`, `ready`, `document_revision = revision = indexed_revision` и выбранную модель. Ответ наставника становится доступен другому стажёру только после публикации и успешной индексации.

## 6. Архивирование, история и эксплуатация

- Пользователи и команды деактивируются, планы, беседы и документы архивируются. Исторические ссылки сохраняются; изменение `active` не удаляет действия и сообщения.
- Наставник видит своих текущих стажёров и назначенные ему доступные эскалации. Доступ к сохранённому снимку повторно проверяется на чтении; смена назначения не открывает всю историю чата.
- Чат и журнал действий доступны после перезагрузки браузера без Redis-буфера. Успешный ответ не зависит от существования live Pub/Sub-подписки.
- Удаление пользовательских данных каскадом в MVP не предусмотрено. Полный сброс тестовой БД является отдельной явно выполняемой операцией, а не публичным методом репозитория.
- `events` и `task_status_history` дописываются, а не переписываются при редактировании текущего состояния. Срок хранения/очистка согласуются отдельно; автоматическая очистка истории в первой миграции не включается.
- Установка расширения `vector` и миграции схемы выполняются отдельно от приложения. Runtime не получает автоматически право создавать расширения и менять схему.
- Модели хранения PostgreSQL и JSON-поля не должны становиться доменными моделями Go. Репозитории реализуют нужные сценариям порты; проверка прав и переходов состояния остаётся в прикладном слое, а выбор реализаций производится в точке сборки приложения.

## 7. Проверка покрытия сценариев MVP

| Сценарий | Хранение и ожидаемое поведение |
|----------|------------------------------|
| S-1: панель и статус задачи | `onboarding_plans`, `tasks`, `task_kb_documents`, `task_status_history`. Повтор не создаёт новый переход; конфликт версий не перетирает изменение. Задача организации работы с наставником назначена стажёру и видна наставнику без копии. Материалов может быть несколько. Дедлайны считаются по календарным правилам, после перезагрузки состояние сохранено. |
| S-2: вопрос по базе знаний | `conversations`, `chat_requests`, `chat_messages`, `kb_documents`, `kb_chunks`. Ответ и источники сохранены с редакцией поиска; обновление документа во время генерации не подменяет цитату. Ошибки и частичные ответы не становятся успешной историей. E5 выдаёт векторы длины 768. |
| S-3: отгул | `actions_log`. До подтверждения нет эффекта, одна карточка на `(request_id, proposal_seq)`, один устойчивый ключ на действие, корпоративный статус отделён от выполнения инструмента. |
| S-SEC: отказ по правам | Составные FK сохраняют принадлежность команде; Go проверяет роль/владельца/назначение; `policy_denied` не раскрывает чужие данные. |
| S-5: вопрос наставнику | `actions_log` и `escalations`. Подтверждённая передача, один получатель и ограниченный снимок контекста, повтор не создаёт дубль. |
| S-6: ответ в KB | `escalations`, `kb_documents`, `kb_chunks`. Одна публикация на эскалацию, явные редакции, видимость только после индексации и в разрешённой команде. |
| Метрики и флаги | `events`, `feature_flags`. Повторы запросов не удваивают события; процент прогресса считается по текущим задачам; флаги не подменяют права. |
| Перезапуск Go / обрыв SSE | Терминальные запросы и действия восстанавливаются из PostgreSQL; активные запросы при потере буфера завершаются ошибкой по правилам контракта. |

## 8. Перед первой миграцией

1. Использовать `vector(768)` и профиль `intfloat/multilingual-e5-base` с зафиксированной ревизией весов. Проверить префиксы E5, L2-нормализацию и cosine distance на тестовых вопросах. Top-k и порог уточняются как настройки RAG, а не как отсутствующие параметры SQL-типа.
2. Синхронизировать актуальный Go/Python-контракт в PR #60 с принятыми UUID и `sources[].revision`, проверить обработку терминальных состояний, `seq`, дедлайнов и SSE. Логины и условные префиксы из старых примеров не загружаются как UUID.
3. Подготовить seed с понедельником в `start_date`, календарными дедлайнами по таблице примеров, стабильными ключами задач и связями материалов через `task_kb_documents`. Назначить стажёра ответственным за задачу «Организовать работу с наставником». Уточнения перенести в исходный документ чек-листа. С аналитиком согласовать каталог событий и формулы метрик.
4. Согласовать схемы параметров/результатов MCP, в том числе идемпотентность мока отсутствий. Не выдавать SQL-уникальность за гарантию внешней интеграции.
5. Реализовать DDL в порядке зависимостей, включая составные `UNIQUE` до соответствующих FK. `task_kb_documents` создаётся после задач и KB-документов. Подготовить повторяемый seed с UUID и стабильными `code`/`login`/`seed_key`, заполнить код и timezone каждой команды. Миграции и seed авторизации не включают пароли или приглашения.
6. На отдельной тестовой БД проверить FK другой команды, уникальность пары задача/документ и её позиции, активные уникальности, nullable-области флагов, атомарность истории, параллельное подтверждение, восстановление генерации и повтор публикации ответа. Дополнительно проверить все семь дней старта и сохранение редакции источника при конкурентном обновлении документа. Это требования к будущей миграции/репозиториям; SQL-проверки не считаются выполненными этим документом.
