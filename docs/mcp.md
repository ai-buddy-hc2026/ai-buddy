# Внутренние MCP-инструменты Go

Реализация задач #39 и #40 в ветке `codex/mcp-tools`. База - открытый PR #82
с policy-слоем, который зависит от #80 и #79. Эти зависимости на момент начала
работы не влиты в main. Python tool-calling и полный UI подтверждения сюда не входят.

## Транспорт и доверенный контекст

Endpoint: `http://backend:8080/internal/mcp` внутри Compose. Streamable HTTP,
stateless, JSON-ответы, официальный `modelcontextprotocol/go-sdk` v1.8.0.
Поддерживаются стандартные initialize, tools/list и tools/call, включая согласование
версии протокола SDK. Это отдельный транспорт от SSE чата.

На каждом HTTP-запросе, включая initialize и tools/list, обязательны:

```text
Authorization: Bearer <MCP_SERVICE_TOKEN>
X-Request-ID: <UUID сохраненного chat_requests>
```

Токен задает доверенный вызывающий Go/Python, не LLM и не браузер. Он должен быть
отдельным от AI_SERVICE_TOKEN и JWT_SIGNING_KEY, не короче 32 байт, без пробелов.
Без MCP_SERVICE_TOKEN endpoint выключен. Параметры URL и Origin не принимаются.
Размер тела ограничен 64 KiB, таймаут обработки - 15 секунд.

Go находит пользователя через сохраненный request_id, повторно читает активность
пользователя/команды, роль, владельца, назначения и область инструмента. user_id,
role, team_id, подтверждение и ключ идемпотентности из аргументов не принимаются.
Сервисный токен дает доступ к внутреннему транспорту, но не заменяет эти проверки.
Контекст MCP-сессии не переносит права между запросами.

Читающие вызовы требуют running и непросроченного deadline_at. Изменяющие вызовы
проверяют сохраненное подтвержденное действие и могут выполняться после завершения
генерации: пользователь подтверждает карточку уже после ответа агента.

## Инструменты и права

Все аргументы - JSON-объекты. Неизвестные поля и null отклоняются. Все внутренние
идентификаторы - UUID. Пустой необязательный ID означает текущего пользователя.

| Имя | Аргументы | Результат | Область доступа |
|-----|-----------|-----------|-----------------|
| `checklist.get_plan` | `intern_id?` | Существующая схема Plan: stages, tasks, progress, next_task_id | intern - свой план; buddy - назначенные стажеры; lead - своя команда. Для buddy/lead intern_id обязателен |
| `checklist.update_status` | `action_id` | Существующая схема Task | Только исполнитель в доступном плане, сохраненное подтверждение обязательно |
| `employees.get_manager` | `employee_id?` | `{id, name}` | Только свой руководитель из manager_id, активный buddy/lead той же команды |
| `absences.get_policy` | `{}` | `{revision, title, types, max_advance_days, timezone}` | Своя команда, timezone текущего пользователя с fallback команды |
| `absences.list_for_employee` | `employee_id?` | `{items: [{id, date, type, status, approver}]}` | Только свои отсутствия, для всех ролей |
| `absences.create_request` | `action_id` | `{id: "ABS-0001", date, type, status: "pending_approval", approver}` | Только за себя, сохраненное подтверждение обязательно |

Список содержит все шесть инструментов; фильтрация данных и проверка конкретного
вызова выполняются в Go. Совпадение роли или команды само по себе не дает доступа
к чужим отсутствиям. Результат списка отсортирован по дате и внутреннему номеру
по убыванию; пустой список - `items: []`. Нумерация ABS может иметь пропуски.

## Подтверждение и выполнение

MCP не создает и не подтверждает actions_log. Это обязанность будущего обработчика
action_proposal и UI endpoint подтверждения, описанных в ai-contract.md. В этой
ветке их нет; интеграционные тесты создают подтверждения доверенной SQL-фикстурой.

Для `absences.create_request` сохраненные parameters:

```json
{"date":"2026-11-12","type":"отгул","approver":"10000000-0000-0000-0000-000000000003"}
```

Для `checklist.update_status`:

```json
{"task_id":"30000000-0000-0000-0000-000000000001","status":"done","version":1}
```

UUID в примерах иллюстрируют формат, а не гарантируют наличие записи в seed.
При будущем подключении UI изменение статуса через MCP тоже требует отдельного
сохраненного подтверждения. Текущий прямой PATCH /tasks/{id} остается явной
операцией пользователя и не заменяется MCP-вызовом.

Действие должно принадлежать пользователю и request_id вызова, иметь совпадающий
action_type, confirmed_by=actor_id и confirmed_at. Разрешены confirmed, failed
для повтора или succeeded для выдачи сохраненного результата. proposed,
cancelled и executing не исполняются. Подтвержденные параметры, автор, тип,
согласовавший пользователь и ключ защищены триггером от замены. Успешное действие
неизменяемо. UNIQUE(idempotency_key) исключает назначение того же ключа другому действию.

Исполнитель блокирует строку действия, повторно проверяет текущие права, затем
атомарно сохраняет изменение, результат и succeeded. Для чек-листа в ту же
транзакцию входят version, история статуса и task_status_changed. Конкурентные
повторы одного action_id ждут блокировку и получают исходный результат без
новой заявки или версии задачи. Результат и ключ переживают перезапуск Go.

При штатном сбое инструмент сохраняет failed, last_error, attempt_count и событие
action_failed. Следующая попытка использует тот же ключ. Ошибка SQL откатывает
транзакцию целиком; частичный успех задачи или отсутствия не сохраняется.
Отказ policy откатывает операцию и отдельно сохраняет policy_denied.

Это гарантия локального синтетического сервиса, работающего в одной PostgreSQL
транзакции. Она не описывает гарантию будущей внешней HR-интеграции.

## Синтетические правила отсутствий

Это тестовая инструкция, не регламент Авито. Поддерживается один день отсутствия,
типы `отгул` и `отпуск`. Дата YYYY-MM-DD должна находиться между сегодняшним днем
и 365 днями вперед включительно, в timezone пользователя. Многодневные интервалы,
балансы отпусков, праздники и одобрение руководителем не моделируются.

Согласующий определяется по актуальному manager_id. Если сохраненный approver
отличается от текущего, выполнение возвращает IDEMPOTENCY_CONFLICT: требуется
новое предложение и подтверждение, параметры старого действия не переписываются.
Повтор succeeded возвращает ранее сохраненный результат, даже если дата прошла
или назначение руководителя изменилось. Текущий доступ пользователя проверяется.

ABSENCES_FAIL_RATE принимает число 0-1: 0 - без искусственных сбоев, 1 - каждый
новый вызов создания завершается TOOL_UNAVAILABLE до вставки отсутствия.
Уже успешный повтор не зависит от вероятности сбоя. Поле status=pending_approval
означает, что заявка создана, а не одобрена руководителем.

## Ошибки и проверки

Ошибки инструментов возвращаются как MCP CallToolResult с isError=true, без SQL,
служебных токенов и чужих данных. Коды: INVALID_ARGUMENT, INVALID_CONTEXT,
POLICY_DENIED, CONFIRMATION_REQUIRED, IDEMPOTENCY_CONFLICT, MANAGER_NOT_ASSIGNED,
VERSION_CONFLICT, PLAN_NOT_ACTIVE, TOOL_UNAVAILABLE. Ошибки JSON Schema могут
отклоняться самим SDK до обработчика. Неизвестное имя не исполняется.

Ошибка аутентификации транспорта дает HTTP 401, неверный/недоступный сохраненный
контекст - 403, неверные заголовки/URL - 400, недоступная БД - 503.

Из backend:

```powershell
go test ./...
go vet ./...
golangci-lint run
```

Для реальных проверок БД задать TEST_DATABASE_URL на отдельную тестовую БД.
Тесты используют собственные временные схемы. TestMCPListAndCall работает без БД
и проверяет настоящий HTTP-транспорт официальным MCP-клиентом. Интеграционные
тесты Tools проверяют миграцию, конкурентный повтор, подтверждение, смену прав,
откат изменения задачи и повтор после синтетического сбоя. TEST_REDIS_URL нужен
для остальных тестов чата, но не для самих MCP-инструментов.
