# События `events`

Документ описывает прикладные события для метрик и аудита отказов. События
неизменяемы. Потоковые события Python/Redis/SSE (`token`, `tool_call`,
`action_proposal`, `done`, `error`) не являются строками этой таблицы.

## Общие поля

| Поле             | Тип           |Назначение                                                                          |
| ---------------- | ------------- | ----------------------------------------------------------------------------------- |
| `id`             | `uuid`       | Уникальный идентификатор события, первичный ключ.                                   |
| `team_id`        | `uuid`            | Команда, к которой относится событие.                                               |
| `actor_id`       | `uuid`              | Пользователь, инициировавший событие. Для системных событий `NULL`.                 |
| `request_id`     | `uuid`               | Идентификатор генерации ответа или связанного запроса.                              |
| `action_id`      | `uuid`              | Идентификатор действия, если событие связано с действием.                           |
| `task_id`        | `uuid`               | Идентификатор задачи, если событие связано с задачей.                               |
| `event_type`     | `text`            | Код события из каталога.                               |
| `schema_version` | `smallint`        | Версия структуры `payload`, по умолчанию `1`. Значение не меньше `1`.               |
| `dedup_key`      | `text`              | Устойчивый ключ для защиты от повторной записи. Должен быть уникальным, если задан. |
| `payload`        | `jsonb`           | Дополнительные разрешённые данные события. По умолчанию `{}`.                       |
| `created_at`     | `timestamptz`    | Время записи события в PostgreSQL.                                                  |

`team_id` ограничивает область события. Связанные `actor_id`, `request_id`,
`action_id` и `task_id` должны принадлежать той же команде. Неверный или чужой
идентификатор не записывается как успешное событие. Отказ по правам
фиксируется в области инициатора без раскрытия чужих данных.

В `payload` нельзя сохранять полный текст чата, токены доступа и секретные
параметры. Для связи и повторной обработки используются UUID из общих полей,
а не дублирование больших объектов в `payload`.

## Каталог и момент записи

| Событие               | Связанные поля                                                             | Когда записывается                                                                                                                            | Минимальный `payload`                                                      |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `chat_question`       | `team_id`, `actor_id`, `request_id`                                        | Одновременно с созданием `chat_requests` и пользовательского сообщения, после проверки доступа.                                                   | `conversation_id`.                                                          |
| `answer_completed`    | `team_id`, `actor_id`, `request_id`                                        | После сохранения результата обработки вопроса, независимо от статуса ответа и наличия источников.                                               | `answer_status`, `question_category`.                                      |
| `answer_with_source`  | `team_id`, `actor_id`, `request_id`                                        | Дополнительно к `answer_completed` при сохранении успешного ответа, если ответ содержит хотя бы один подтверждённый источник.                  | Идентификаторы документов и их `revision`, количество источников.          |
| `action_proposed`     | `team_id`, `actor_id`, `request_id`, `action_id`                           | После сохранения предложения действия со статусом `proposed` и до показа карточки в UI.                                                       | `action_type`, `proposal_seq`, безопасное описание параметров.             |
| `action_confirmed`    | `team_id`, `actor_id`, `request_id`, `action_id`                           | После повторной проверки пользователя и параметров, при атомарной фиксации подтверждения и резервировании выполнения.                         | Тип действия и подтверждённый переход состояния.                           |
| `action_failed`       | `team_id`, `actor_id`, `request_id`, `action_id`                           | После каждой неуспешной попытки выполнения или после фиксации ошибки выполнения действия.                                                     | `attempt`, код ошибки, безопасное сообщение и состояние действия.            |
| `escalation_created`  | `team_id`, `actor_id`, `request_id`, `action_id`                           | После создания эскалации наставнику. Для действия передачи вопроса запись выполняется в одной транзакции с результатом действия и эскалацией. | `escalation_id`, идентификатор назначенного наставника, безопасный статус. |
| `policy_denied`       | `team_id`, `actor_id`, при наличии `request_id`, `action_id` или `task_id` | Сразу после отказа по роли, владельцу, назначению или принадлежности к команде.                                                               | `operation` и `reason`, без чужих данных.                                   |
| `task_status_changed` | `team_id`, `actor_id`, `task_id`                                           | В одной транзакции с условным изменением задачи и добавлением строки в `task_status_history`.                                                 | Предыдущий и новый статус, версия задачи, причина перехода.                |

### Допустимые значения payload

Для `answer_completed` используются значения, переданные AI-service:

- `question_category`: `task`, `process`, `access`, `technical`, `other`;
- `answer_status`: `answered` или `unknown`.

Go не определяет эти значения по тексту ответа. Категорию определяет
AI-service и передаёт в Go вместе с явным `answer_status`; оба значения
записываются в `answer_completed`. При наличии источников дополнительно
записывается `answer_with_source`. Отдельное событие `answer_unknown` не
создаётся.

Для `policy_denied`:

- `operation`: `checklist.get_plan`, `checklist.update_status`,
  `knowledge.search`, `employees.get_manager`, `absences.get_policy`,
  `absences.create_request`, `absences.list_for_employee`,
  `escalation.create`;
- `reason`: `role_forbidden`, `not_owner`, `not_assigned`,
  `not_team_member`, `invalid_scope`.

Go проверяет оба поля по этим спискам до записи события. Новое значение
сначала добавляется в этот каталог и контракт Go, а не передаётся произвольной
строкой.

Для `action_failed` номер попытки - положительное целое `attempt`, начиная с
`1`. Устойчивый ключ имеет формат
`action:<action_id>:attempt:<attempt>:failed`; поэтому разные неудачные попытки
одного действия являются разными событиями.

## Транзакции и повторы

- Событие, связанное с изменением данных, записывается в той же транзакции,
  что и это изменение.
- `chat_question` и создание пользовательского сообщения не должны
  разделяться частичным коммитом.
- `action_proposed` записывается до выдачи карточки. Без этой записи действие
  нельзя считать доступным для подтверждения.
- Повтор подтверждения того же `action_id` не создаёт второе
  `action_confirmed` и не запускает действие повторно.
- Повтор одного перехода статуса задачи не создаёт новое событие, если статус
  и версия не изменились.
- Для повторяемых операций используется `dedup_key`, например
  `request:<uuid>:chat_question`,
  `request:<uuid>:answer_completed`,
  `action:<action_id>:attempt:<n>:failed`,
  `request:<uuid>:action_proposed` или
  `task:<uuid>:version:<n>:status_changed`.
- Закрытие SSE не является моментом записи события. Источник истины для
  истории - PostgreSQL.

## Индексы и аудит

Рекомендуются индексы:

- `(team_id, event_type, created_at, id)`;
- `(actor_id, created_at, id)` для непустого `actor_id`;
- `(request_id)`, `(action_id)` и `(task_id)` для непустых значений.

События должны содержать только минимальные данные, необходимые для метрик, аудита и восстановления связи с доменными сущностями.
