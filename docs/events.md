# События `events`

Документ описывает прикладные события для метрик и аудита отказов. События
неизменяемы. Потоковые события Python/Redis/SSE (`token`, `tool_call`,
`action_proposal`, `done`, `error`) не являются строками этой таблицы.

## Общие поля

| Поле | Тип | Обязательность | Назначение |
|---|---|---|---|
| `id` | `uuid` | обязательно | Уникальный идентификатор события, первичный ключ. |
| `team_id` | `uuid` | обязательно | Команда, к которой относится событие. |
| `actor_id` | `uuid` | nullable | Пользователь, инициировавший событие. Для системных событий `NULL`. |
| `request_id` | `uuid` | nullable | Идентификатор генерации ответа или связанного запроса. |
| `action_id` | `uuid` | nullable | Идентификатор действия, если событие связано с действием. |
| `task_id` | `uuid` | nullable | Идентификатор задачи, если событие связано с задачей. |
| `event_type` | `text` | обязательно | Код события из каталога ниже. Это не PostgreSQL enum. |
| `schema_version` | `smallint` | обязательно | Версия структуры `payload`, по умолчанию `1`. Значение не меньше `1`. |
| `dedup_key` | `text` | nullable | Устойчивый ключ для защиты от повторной записи. Должен быть уникальным, если задан. |
| `payload` | `jsonb` | обязательно | Дополнительные разрешённые данные события. По умолчанию `{}`. |
| `created_at` | `timestamptz` | обязательно | Время записи события в PostgreSQL. |

`team_id` ограничивает область события. Связанные `actor_id`, `request_id`,
`action_id` и `task_id` должны принадлежать той же команде. Неверный или чужой
идентификатор не записывается как успешное событие. Отказ по правам
фиксируется в области инициатора без раскрытия чужих данных.

В `payload` нельзя сохранять полный текст чата, токены доступа и секретные
параметры. Для связи и повторной обработки используются UUID из общих полей,
а не дублирование больших объектов в `payload`.

## Каталог и момент записи

| Событие | Когда записывается | Связанные поля | Минимальный `payload` |
|---|---|---|---|
| `chat_question` | Атомарно с созданием `chat_requests` и пользовательского сообщения, после проверки доступа. | `team_id`, `actor_id`, `request_id` | `conversation_id`, безопасная классификация вопроса. |
| `answer_with_source` | При сохранении успешного ответа, если ответ содержит хотя бы один подтверждённый источник. | `team_id`, `actor_id`, `request_id` | Идентификаторы документов и их `revision`, количество источников. |
| `answer_unknown` | При явном результате «ответ не найден». Пустой массив источников сам по себе не является основанием. | `team_id`, `actor_id`, `request_id` | Причина отсутствия ответа, без выдуманного источника. |
| `action_proposed` | После сохранения предложения действия со статусом `proposed` и до показа карточки в UI. | `team_id`, `actor_id`, `request_id`, `action_id` | `action_type`, `proposal_seq`, безопасное описание параметров. |
| `action_confirmed` | После повторной проверки пользователя и параметров, при атомарной фиксации подтверждения и резервировании выполнения. | `team_id`, `actor_id`, `request_id`, `action_id` | Тип действия и подтверждённый переход состояния. |
| `action_failed` | После неуспешного выполнения или после фиксации ошибки выполнения действия. | `team_id`, `actor_id`, `request_id`, `action_id` | Код ошибки, безопасное сообщение и состояние действия. |
| `escalation_created` | После создания эскалации наставнику. Для действия передачи вопроса запись выполняется в одной транзакции с результатом действия и эскалацией. | `team_id`, `actor_id`, `request_id`, `action_id` | `escalation_id`, идентификатор назначенного наставника, безопасный статус. |
| `policy_denied` | Сразу после отказа по роли, владельцу, назначению или принадлежности к команде. | `team_id`, `actor_id`, при наличии `request_id`, `action_id` или `task_id` | Код политики и тип запрошенного ресурса, без чужих данных. |
| `task_status_changed` | В одной транзакции с условным изменением задачи и добавлением строки в `task_status_history`. | `team_id`, `actor_id`, `task_id` | Предыдущий и новый статус, версия задачи, причина перехода. |

Успешное завершение генерации и наличие источников могут быть зафиксированы
одним `answer_with_source`. Отдельное событие завершения генерации в этот
каталог не входит. Если ответ явно признан неизвестным, записывается
`answer_unknown`, а не событие с источником.

## Транзакции и повторы

- Событие, связанное с изменением данных, записывается в той же транзакции,
  что и это изменение.
- `chat_question` и создание пользовательского сообщения не должны
  разделяться частичным коммитом.
- `action_proposed` записывается до выдачи карточки. Без этой записи действие
  нельзя считать доступным для подтверждения.
- Повтор подтверждения того же `action_id` не создаёт второе
  `action_confirmed` и не запускает действие повторно.
- Повтор одного перехода статуса задачи не создаёт новое событие, если статус
  и версия не изменились.
- Для повторяемых операций используется `dedup_key`, например
  `request:<uuid>:chat_question`,
  `request:<uuid>:action_proposed` или
  `task:<uuid>:version:<n>:status_changed`.
- Закрытие SSE не является моментом записи события. Источник истины для
  истории - PostgreSQL.

## Индексы и аудит

Рекомендуются индексы:

- `(team_id, event_type, created_at, id)`;
- `(actor_id, created_at, id)` для непустого `actor_id`;
- `(request_id)`, `(action_id)` и `(task_id)` для непустых значений.

Таблица не используется как архив каждого токена LLM. События должны
содержать только минимальные данные, необходимые для метрик, аудита и
восстановления связи с доменными сущностями.
