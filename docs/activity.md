# Списки стажеров, действий и эскалации

Реализация в ветке `feat/escalations-actions-api`, база - открытый PR #83.
HTTP-схемы: [openapi.yaml](openapi.yaml), инструменты: [mcp.md](mcp.md).
Зависимости пока не означают наличие этих операций в main.

## Общие правила списков

GET /buddy/interns и GET /actions требуют пользовательский JWT. Go повторно читает
активного пользователя активной команды и проверяет policy. Маршруты работают
без LLM и независимо от MCP_SERVICE_TOKEN. Ответы имеют Cache-Control: no-store.

Общие параметры: limit от 1 до 100, по умолчанию 50, и необязательный cursor.
Пустые значения, неизвестные параметры, повторы параметра и неверный курсор дают 400.
Ответ: `{items: [...], next_cursor: string | null}`. Пустой список имеет items: [].

Курсор подписан HMAC и привязан к типу списка, пользователю, команде и фильтрам.
Используется отдельный производный ключ от JWT_SIGNING_KEY. Смена ключа делает
прежние курсоры недействительными. Курсор не содержит секретов и не дает прав.
Его подмена или применение к другому списку, пользователю либо фильтрам дают 400.
Между страницами можно менять limit. Пагинация использует ключ последней записи,
а не OFFSET; каждая страница заново проверяет актуальные права и назначения.

## GET /buddy/interns

Только роль buddy. intern и lead получают 403 POLICY_DENIED с событием отказа.
Возвращаются активные пользователи intern той же команды, у которых buddy_id
явно равен текущему пользователю. Совпадения команды недостаточно.
Элементы соответствуют схеме User, порядок id ASC. Прогресс читается через
существующий `/onboarding/plan?intern_id=<uuid>` и не добавляется в User молча.

Отзыв назначения или деактивация исключают стажера из следующей страницы.
Смена роли наставника проверяется и при ранее выданном JWT.

## GET /actions

Все роли читают только свои действия из своей команды. Buddy/lead не получают
историю действий других людей. Дополнительные фильтры: status из ActionStatus
и conversation_id собственной беседы. Чужая и отсутствующая беседа дают одинаковый
404 NOT_FOUND и безопасное policy_denied в области инициатора.

Без фильтра возвращаются действия из всех своих бесед, включая архивные.
Порядок created_at DESC, id DESC. ActionType включает уже реализованный
checklist.update_status. details содержит разрешенные поля карточки из parameters,
result - поля результата инструмента. Ключ идемпотентности и произвольные внутренние
поля не возвращаются. last_error преобразуется в безопасные code/message без SQL
и трассировок. Чтение не меняет состояние и не запускает инструмент повторно.

## MCP escalation.create

Вход - только action_id. В сохраненных подтвержденных parameters:

```json
{"buddy_id":"10000000-0000-0000-0000-000000000002","question":"Как завершить задачу?","context_snapshot":[{"message_id":"60000000-0000-0000-0000-000000000001","role":"user","content":"Нужна помощь","sources":[]}]}
```

Идентификаторы примера иллюстрируют формат. Создавать может только intern за себя.
Получатель должен совпадать с текущим buddy_id, быть активным buddy своей команды.
Вопрос непустой, до 4000 символов. context_snapshot обязателен: пустой массив или
до 10 явно выбранных сообщений, суммарно до 20000 символов, без повторов message_id.

Go сверяет ID, роль и точный текст со своей сохраненной беседой. Сообщение должно
относиться к исходной или более ранней генерации и существовать к моменту
подтверждения. Нельзя подставить чужое, более позднее или произвольное сообщение.
Снимок не дает наставнику доступ ко всей беседе. Пока профиль #24 содержит пустые
sources; непустые источники отклоняются с policy_denied до интеграции прав KB.

Миграция 0006 создает escalations. Результат инструмента:
`{id: UUID, status: "open", buddy_id: UUID}`. Создание эскалации, результата
actions_log и escalation_created атомарно. Блокировка действия и UNIQUE(action_id)
исключают дубли. При смене назначения до выполнения требуется новое предложение
и подтверждение. Повтор succeeded возвращает прежний результат без отправки новому
наставнику, с проверкой текущей роли и доступа инициатора.

## Границы и проверки

Обработчик action_proposal и HTTP/UI подтверждения пока отсутствуют. Тесты создают
подтвержденные действия доверенной SQL-фикстурой; MCP не подтверждает их сам.
GET /buddy/escalations, ответ наставника, внешние уведомления и публикация в KB
не входят в эту ветку. Поля ответа в миграции подготовлены по схеме БД, но это
не означает реализацию обработчиков.

Из backend: go test ./..., go vet ./..., golangci-lint run. Для интеграции задать
TEST_DATABASE_URL на отдельную тестовую БД и запустить go test -race ./internal/database.
Тесты проверяют права, снимок контекста, конкурентные повторы, атомарный откат,
актуальные назначения, фильтры, одинаковый created_at и область курсора.
