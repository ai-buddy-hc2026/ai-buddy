# Списки стажеров, действий и эскалации

Статус: описание действующего поведения Go API. Документ поясняет права,
пагинацию, подтверждения и работу с вопросами наставнику.
HTTP-схемы: [openapi.yaml](openapi.yaml), инструменты: [mcp-contract.md](mcp-contract.md).
Формальные поля и HTTP-коды задаёт OpenAPI; состояние полного MVP описано в
[mvp.md](mvp.md). Наличие внутреннего исполнителя не означает завершения S-5.

## Общие правила списков

GET /buddy/interns, GET /actions и GET /buddy/escalations требуют пользовательский JWT. Go повторно читает
активного пользователя активной команды и проверяет policy. Маршруты работают
без LLM и независимо от MCP_SERVICE_TOKEN. Ответы имеют Cache-Control: no-store.

Общие параметры: limit от 1 до 100, по умолчанию 50, и необязательный cursor.
Пустые значения, неизвестные параметры, повторы параметра и неверный курсор дают 400.
Ответ: `{items: [...], next_cursor: string | null}`. Пустой список имеет items: [].

Курсор подписан HMAC и привязан к типу списка, пользователю, команде и фильтрам.
Используется отдельный производный ключ от JWT_SIGNING_KEY. Смена ключа делает
прежние курсоры недействительными. Курсор не содержит секретов и не дает прав.
Его подмена или применение к другому списку, пользователю либо фильтрам дают 400.
Между страницами можно менять limit. Пагинация использует ключ последней записи,
а не OFFSET; каждая страница заново проверяет актуальные права и назначения.

## GET /buddy/interns

Только роль buddy. intern и lead получают 403 POLICY_DENIED с событием отказа.
Возвращаются активные пользователи intern той же команды, у которых buddy_id
явно равен текущему пользователю. Совпадения команды недостаточно.
Элементы соответствуют схеме User, порядок id ASC. Прогресс читается через
существующий `/onboarding/plan?intern_id=<uuid>` и не добавляется в User молча.

Отзыв назначения или деактивация исключают стажера из следующей страницы.
Смена роли наставника проверяется и при ранее выданном JWT.

## GET /actions

Все роли читают только свои действия из своей команды. Buddy/lead не получают
историю действий других людей. Дополнительные фильтры: status из ActionStatus
и conversation_id собственной беседы. Чужая и отсутствующая беседа дают одинаковый
404 NOT_FOUND и безопасное policy_denied в области инициатора.

Без фильтра возвращаются действия из всех своих бесед, включая архивные.
Порядок created_at DESC, id DESC. ActionType включает уже реализованный
checklist.update_status. details содержит разрешенные поля карточки из parameters,
result - поля результата инструмента. Ключ идемпотентности и произвольные внутренние
поля не возвращаются. last_error преобразуется в безопасные code/message без SQL
и трассировок. Чтение не меняет состояние и не запускает инструмент повторно.

## Внутренняя операция escalation.create

Операция не входит в базовый список шести MCP tools.
Ее данные и доверенный исполнитель Go сохранены. Публикация из Python требует
отдельного расширения контракта. Вход исполнителя - action_id. В сохраненных подтвержденных parameters:

```json
{"buddy_id":"4a59a828-3b1a-55e4-bf9b-81db5ad6183a","question":"Как завершить задачу?","context_snapshot":[{"message_id":"60000000-0000-0000-0000-000000000001","role":"user","content":"Нужна помощь","sources":[]}]}
```

Идентификаторы примера иллюстрируют формат. Создавать может только intern за себя.
Получатель должен совпадать с текущим buddy_id, быть активным buddy своей команды.
Вопрос непустой, до 4000 символов. context_snapshot обязателен: пустой массив или
до 10 явно выбранных сообщений, суммарно до 20000 символов, без повторов message_id.

Go сверяет ID, роль и точный текст со своей сохраненной беседой. Сообщение должно
относиться к исходной или более ранней генерации и существовать к моменту
подтверждения. Нельзя подставить чужое, более позднее или произвольное сообщение.
Снимок не дает наставнику доступ ко всей беседе. Именно исполнитель эскалации
принимает только пустые sources и сообщения с пустыми источниками в БД; непустые
источники отклоняются с policy_denied. Это ограничение снимка, а не всего чата:
обычная история чата уже поддерживает проверенные RAG-источники.

Миграция 0006 создает escalations. Результат инструмента:
`{id: UUID, status: "open", buddy_id: UUID}`. Создание эскалации, результата
actions_log и escalation_created атомарно. Блокировка действия и UNIQUE(action_id)
исключают дубли. При смене назначения до выполнения требуется новое предложение
и подтверждение. Повтор succeeded возвращает прежний результат без отправки новому
наставнику, с проверкой текущей роли и доступа инициатора.

## POST /actions/{id}/confirm

JWT, UUID действия, без тела и query-параметров. Подтверждать может только владелец
после явного действия в UI. Go повторно проверяет актуальные права и параметры.
Карточка неизменяема; изменение параметров требует нового предложения.
Ключ идемпотентности создаётся Go один раз и не передаётся клиентом.

- Сохранённый итог возвращается как Action с HTTP 200, включая failed с last_error.
- confirmed/executing возвращаются с HTTP 202; состояние читается через GET /actions.
- Повтор succeeded возвращает сохранённый результат. failed допускает повтор с тем же ключом.
- cancelled даёт 409 ACTION_NOT_CONFIRMABLE; чужое/отсутствующее действие - 404.
- Сбой проверки/хранилища до сохранения результата даёт 503, а не ложный успех.

Два агентных действия базового профиля: checklist.update_status и absences.create_request.
UI подтверждения подключён. Внутренний исполнитель escalation.create также сохранён,
но предложение этой операции из Python пока не принимается.

## GET /buddy/escalations

Только buddy. Возвращаются вопросы его команды, у которых и сохранённый buddy_id,
и текущее назначение активного стажёра совпадают с пользователем. После смены
назначения прежний наставник теряет доступ; история автоматически новому не передаётся.

Фильтры: необязательные intern_id (UUID) и status (open/answered/closed), limit/cursor
по общим правилам. Корректный чужой или неназначенный intern_id даёт пустой список,
а не 404. Курсор привязан также к intern_id/status. Порядок created_at DESC, id DESC.

Элемент содержит вопрос, ограниченный context_snapshot, ответ и nullable publication.
version - непрозрачная строка из updated_at; клиент возвращает её при ответе.
publication содержит document_id, revision, status, index_status, indexed_revision,
index_error. Отсутствующая публикация представлена null. Это не доступ ко всей беседе.
Endpoint закрытия эскалации не реализован, хотя closed является допустимым состоянием.

## POST /buddy/escalations/{id}/answer

Только актуальный назначенный buddy. Тело application/json содержит ровно:

```json
{"answer_text":"Обсуди следующий шаг на встрече с наставником.","add_to_kb":true,"version":"2026-11-15T10:00:00Z"}
```

Версия в примере иллюстративная: использовать значение из GET /buddy/escalations.
answer_text - непустой UTF-8 текст до 20000 символов; add_to_kb обязателен;
version - строка длиной 1-64. Неизвестные поля, неверный UUID и query-параметры дают 400.

Go блокирует эскалацию, проверяет команду, роль и текущее назначение. Неверная роль
даёт 403; отсутствующая/недоступная эскалация или потеря назначения - 404.
Закрытая эскалация либо конфликт изменения дают 409 VERSION_CONFLICT.

При актуальной version сохраняются ответ, автор, время и новая version. Повтор
того же ответа не создаёт дубль. При устаревшей version допустим прежний текст,
если add_to_kb=false либо публикация уже существует; запрос новой публикации
с устаревшей version отклоняется. false не удаляет и не обновляет существующую KB.
Поле add_to_kb в ответе означает наличие публикации, поэтому может быть true
даже при false во входе. Изменённый ответ требует актуальной version.

При add_to_kb=true Go одной транзакцией сохраняет ответ и published-документ,
добавляя тестовую пометку. Одна эскалация имеет один документ; изменение контента
увеличивает revision. Ответ возвращает kb_document_id и kb_status (not_added либо
состояние индекса документа), а также актуальную version.

## Публикация и поиск KB

Go сразу создаёт полнотекстовый индекс и отмечает документ ready с indexed_revision.
Стажёр команды может искать его через GET /knowledge/search?q=...; endpoint требует
непустой запрос до 250 символов и возвращает до 10 документов с источниками.

Чат использует отдельный векторный поиск Python. Перед каждым поиском Python проверяет
область доступа через Go /mcp/knowledge-scope и индексирует новые редакции ответов
наставника. ready полнотекстового документа само по себе не доказывает наличие
векторных чанков. Источник ответа сохраняет revision использованного материала.

## Границы и проверки

Списки, подтверждение действий базового профиля, ответ наставника и публикация
подключены к UI. S-5 из Python не завершён: тесты внутреннего исполнителя используют
SQL-фикстуры подтверждённых действий. Полная цепочка S-6 зависит от S-5; фикстуру
нельзя выдавать за успешную передачу вопроса из чата. Внешних уведомлений нет.

Проверки из backend:

```bash
go test ./internal/httpapi ./internal/chat ./internal/toolcontract
go vet ./internal/httpapi ./internal/chat ./internal/toolcontract
```

Для проверок БД задать TEST_DATABASE_URL на отдельную синтетическую базу и выполнить
`go test -race ./internal/database`. Для сценариев Redis также нужен TEST_REDIS_URL.
Без переменных соответствующие интеграционные тесты пропускаются. Тесты проверяют
права, снимок контекста, повторы, откат, назначения, курсоры и версии публикации.
Команды и полный набор проверок: [backend README](../backend/README.md#проверки).
