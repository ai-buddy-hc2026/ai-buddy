# Календарь доступности

Первая версия продолжает справочник из [PR #105](https://github.com/ai-buddy-hc2026/ai-buddy/pull/105).
Имитация корпоративного календаря находится в Go/PostgreSQL за интерфейсом
CalendarStore. Это приёмные часы, а не копия всего календаря сотрудника.
MCP-инструменты, уведомления, отмена/перенос встречи и внешняя доставка приглашений
в эту поставку не входят. Подтверждённая бронь - результат мока, а не отправленное
сообщение во внешнюю систему.

## Сценарий

1. В «Люди / Приёмные часы» пользователь выбирает коллегу своей команды.
2. Go показывает свободные приёмные слоты на ближайшие 14 дней. Содержание и
   участники чужих встреч не раскрываются. Время подписано часовым поясом коллеги.
3. Выбор слота открывает черновик с темой. До «Записаться» изменений в БД нет.
4. Подтверждение сохраняет ключ повтора в браузере и создаёт бронь через Go.
5. Показываются ID и confirmed. Встреча сохраняется после перезагрузки, видна
   в «Моих встречах» и плане онбординга. Наставник с учётной записью видит эту же
   встречу в «Моих встречах» на экране наставника, без копии данных. Раздел
   «Люди» остаётся доступным по прежним правилам, права навигации не расширяются.
6. При конфликте список доступности обновляется. При неопределённом результате
   пользователь проверяет встречи либо повторяет запрос с тем же ключом.

Проверяется доступность обоих участников по броням мока. Занятость из других
реальных календарей не подключена. Если приёмных часов или общего времени нет,
интерфейс показывает пустое состояние. Ошибки API не подменяются frontend-моком.

## HTTP API

Все операции требуют Bearer JWT. Команда, участник и права определяются в Go
по актуальной БД. Intern, buddy и lead могут записывать только себя. Поля
attendee_id, user_id, team_id в POST запрещены. Бронь к самому себе запрещена.

| Endpoint | Назначение |
|----------|------------|
| GET /calendar/{employee_id}/office-hours | Доступные приёмные слоты активного коллеги своей команды. |
| GET /calendar/bookings | Встречи текущего пользователя как гостя или принимающего коллеги. |
| POST /calendar/bookings | Подтверждение брони с Idempotency-Key. |

GET принимают необязательную пару from/to в RFC3339 со смещением. Без обоих -
сейчас и следующие 14 дней; указать только одну границу нельзя. Интервал
не длиннее 31*24 часов, from < to. Слоты отбираются по starts_at в [from,to)
и не могут начинаться в прошлом. Встречи отбираются по пересечению с [from,to).
Лимит ответа - 200 записей; при превышении 400, нужно сузить интервал. Скрытого
усечения нет. Сортировка: starts_at, id. Пустой ответ: `{"items":[]}`.

POST принимает ровно:

```json
{
  "slot_id": "30000000-0000-4000-8000-000000000001",
  "topic": "Первая задача",
  "confirmed": true
}
```

Idempotency-Key - ненулевой UUID, сохраняемый до отправки запроса. Успех и
повтор возвращают 200 с одной и той же бронью. Повтор после начала встречи
также возвращает сохранённый результат, пока участник имеет право читать его.
Тот же ключ с другим слотом или темой даёт 409 IDEMPOTENCY_CONFLICT.
confirmed=false, отсутствие ключа, неверный UUID/интервал, лишние/повторные
параметры и лишние JSON-поля дают 400. Чужой, скрытый и отсутствующий ресурс -
одинаковый 404. Занятый, истёкший или пересекающийся слот - 409 SLOT_UNAVAILABLE.
Недоступность сервиса - 503, успех не заявляется. Ответы имеют Cache-Control: no-store.

## Сохранность и конкуренция

Бронирование атомарно в PostgreSQL. Участники блокируются транзакционными
advisory-lock в порядке UUID, затем блокируется слот и повторно проверяется
доступность. Это защищает от одновременной брони одного слота, разных
пересекающихся слотов одного коллеги и записи гостя к двум людям одновременно.
Соседние встречи, где конец одной равен началу другой, не пересекаются.
UNIQUE(slot_id) и UNIQUE(attendee_id,idempotency_key) служат дополнительной защитой.

Бронь хранит снимок времени, часового пояса и имён участников. Деактивация
коллеги скрывает новые слоты, но не удаляет историю гостя. Чтение чужих броней
не разрешается даже руководителю. При повторе проверяется актуальный пользователь.

Frontend хранит неподтверждённый результат по user_id/slot_id в localStorage:
тема и ключ остаются прежними после ошибки или перезагрузки. Если сохранить
ключ не удалось, POST не отправляется. После успеха черновик удаляется.
Кэши запросов включают пользователя, при выходе очищаются общим механизмом.
Поздний результат старой сессии не подставляется в данные нового пользователя.

## Синтетическое расписание

`backend/internal/database/seeds/calendar.json` содержит office_hours:

```json
{
  "office_hours": [
    {
      "employee_id": "4a59a828-3b1a-55e4-bf9b-81db5ad6183a",
      "weekdays": [2, 4],
      "start_local": "15:00",
      "minutes": 30
    }
  ]
}
```

Дни 1-7 означают понедельник-воскресенье. start_local - HH:MM; длительность
5-240 минут. UUID берутся из справочника. Неизвестный ID - ошибка подготовки БД;
неактивный коллега пропускается. Часовой пояс - users.timezone связанного
пользователя либо teams.timezone. Go разворачивает будущие слоты на 21 день
от текущей даты в этом поясе. Несуществующее локальное время при переходе часов
пропускается. История не удаляется, существующие времена/ID не перезаписываются.

Для продления демонстрационного горизонта повторить db-init. Это начальное
наполнение мока, а не планировщик и не реальная интеграция. После изменения JSON
нужна пересборка db-init. Редактирование уже созданных слотов требует явной
миграции данных с учётом броней.

## Проверки

На отдельной БД с TEST_DATABASE_URL: `go test ./internal/database -run TestCalendar -v`.
Проверяются конкурентная бронь, повтор одного запроса, другой payload с тем же
ключом, пересечения обоих участников, права, прошедшие слоты и часовые пояса.
Frontend: тесты remote-calendar и RemoteHoursTab, Playwright через настоящий Go.
Схемы: [db.md](db.md), [OpenAPI](openapi.yaml).
