# Кейс хакатона: AI-buddy

## Источник и назначение

Рабочий пересказ требований кейса Авито для Hack&Change 2026. Источник: предоставленный команде PDF `Авито_кейс.pdf`, 19 страниц. Оригинал хранится у команды; бинарный файл сюда не включён. Это не дословная копия и не замена актуальным объявлениям организаторов.

Требования сверены по страницам 7-14, контекст по страницам 3-6, справочные материалы по странице 15. Страницы 16-19 содержат сведения о компании, а не дополнительные требования к реализации.

Выбранный командой объём находится в [MVP](../mvp.md), состояние реализации в [README](../../README.md). Требования организаторов, решения команды и уже работающие возможности не следует смешивать.

## Задача и аудитория

Разработать помощника, который помогает стажёру освоиться в команде: найти инструкции, понять этапы адаптации и следующие шаги, получить ответ с учётом контекста и выполнить действие через корпоративный сервис или его имитацию.

Основной пользователь - стажёр. Наставник и руководитель участвуют в подходящих сценариях. Помощник уменьшает повторяющиеся вопросы и организационную работу, но не заменяет общение с наставником.

Кейс приводит оценку занятости наставника: 40-48 часов за шестимесячную программу и 55-65 часов за девятимесячную. Это ориентир бизнес-контекста, а не измеренный эффект нашего продукта и не время только первых недель.

## Что нужно показать

1. Путь стажёра в первые недели и выбранные сценарии на основе чек-листа, опыта и ожиданий.
2. Ответы о команде и инструментах с учётом контекста пользователя.
3. Все заявленные сценарии; хотя бы один включает действие через корпоративный сервис или мок.
4. Этапы адаптации, статусы задач и следующие шаги.
5. Обоснование архитектуры, работы с правами и подключения сервисов.
6. Метрики пользы и способ проверить эффект на стажёрах.

Кейс предлагает 3-5 сценариев либо один глубоко проработанный. Количество само по себе не даёт преимущество: оценивается полнота выбранного решения. Наш MVP включает пять продуктовых сценариев и сквозную проверку безопасности S-SEC.

Действие считается выполненным, когда сервис или мок вернул результат, помощник показал его и сохранил. Карточки с предложением или текста «заявка отправлена» без результата недостаточно.

## Ограничения и качество

- Используются синтетические или обезличенные данные, тестовые инструкции и моки. Инструкции нельзя выдавать за регламенты Авито.
- Реальные данные сотрудников и собственные полноценные аналоги HR-систем не требуются. Авторизацию, роли и корпоративные сервисы можно имитировать.
- Запрещённые пользователю сведения и операции не раскрываются и не выполняются.
- Сценарии с чувствительными персональными данными и финансовыми операциями исключены.
- Отдельные интерфейсы руководителя и HR не обязательны.
- Тесты должны покрывать более 80% строк прикладного кода команды. Зависимости, сгенерированный код и сами тесты исключаются. Нужен воспроизводимый отчёт.
- AI-сценарии и инструменты разрабатываются по SDD-спецификациям поведения.
- Для простых локальных операций ориентир отклика интерфейса меньше секунды. Долгие вызовы LLM и интеграций не блокируют интерфейс; нужны состояние ожидания и обработка сбоев.

## Технологические ориентиры

Описанный стек Авито: Go, PostgreSQL, Redis, React, TypeScript, TanStack, Zustand, Zod; Python с Flask применяется в отдельных случаях. В инфраструктуре упомянуты Docker, Grafana, Clickstream, RPC/Kafka и CI/CD.

Это ориентиры совместимости, а не требование внедрить каждый компонент. FastAPI, SSE и Redis Pub/Sub относятся к решениям команды. Kafka и полноценные HR-системы ради соответствия списку в MVP не добавляются. При отдельном размещении frontend нужен явный API-клиент.

## Комплект сдачи

На платформу передаётся продуктовая презентация PDF со ссылкой на репозиторий либо ZIP с исходниками и презентацией. Для приватного репозитория предоставляется доступ аккаунту жюри `hack-and-change-2026`.

| Артефакт | Что должно быть доступно |
|----------|-------------------------|
| Прототип | Работающий интерфейс и весь заявленный основной сценарий. |
| Исходники и README | Рабочий запуск, версии зависимостей, тестовые учётные записи, порядок проверки и команды тестов. |
| Спецификации и качество | SDD, тесты и воспроизводимый отчёт о покрытии. |
| Данные и интеграции | Тестовые данные и моки для повторения сценариев. |
| Видео | Путь от запроса до результата; файл либо ссылка в README или на первом слайде. |
| Презентация | Продуктовая презентация в PDF. |
| Внешние API | Сервис, модель, переменные окружения, подключение ключа, пример без секретов; для Docker - файлы запуска. |

Организаторы могут использовать свой доступный ключ внешнего API. После дедлайна версия фиксируется; на финале защищается то же решение. Сроки и изменения порядка сдачи проверяются по актуальным объявлениям. Внутренние даты заморозки команды не являются автоматически дедлайнами организаторов.

## Оценивание

Три основания недопуска из кейса: прототип нельзя запустить или пройти основной сценарий; отсутствуют необходимые исходники/инструкции; нет продуктовой презентации. Остальные недочёты учитываются в соответствующих критериях, а не объявляются дополнительными основаниями недопуска.

| Критерий | Онлайн-этап |
|----------|-------------|
| Внедряемость и интеграции | 30% |
| Пользовательский опыт | 25% |
| Работоспособность сценариев | 20% |
| Техническая реализация | 15% |
| Безопасность и данные | 5% |
| Продуктовая презентация | 5% |

На финале: ценность для стажёра и команды 20%, живая демонстрация 25%, обоснованность технических решений 20%, внедряемость и развитие 25%, качество защиты и ответов 5%, командное владение решением 5%. Итог: онлайн-этап 40%, финальная защита 60%.
