# Коллеги команды

Первая версия: список, карточка и буквальный поиск по имени, должности и тегам.
Календарь, уведомления, редактирование через UI и MCP-поиск не входят в поставку.

## Границы и API

`employees` - имитация корпоративного справочника внутри Go/PostgreSQL.
HTTP зависит от интерфейса `EmployeeStore`, текущий адаптер - `database.Listings`.
Его можно заменить корпоративным клиентом, сохранив проверку прав и контракт.
`users` определяет вход и права; `employees` - карточки. Коллега без учётной
записи имеет user_id=null и не получает вход. Категория hr не добавляет JWT-роль.
Для связанной записи employees.id=employees.user_id=users.id. Имена карточек
берутся из employees; права и назначения - из актуальных users.

- `GET /employees?q=мониторинг&limit=50&cursor=...` - список.
- `GET /employees/{id}` - одна карточка.
- Bearer JWT обязателен. Intern, buddy и lead видят активные карточки своей
  команды. Неактивный связанный пользователь также скрывает карточку.
  Доступ к планам, переписке и действиям коллег этим не предоставляется.
- q: до 200 символов, trim и нижний регистр. Буквальная подстрока имени,
  должности или тега; % и _ не шаблоны. Это не семантический поиск вопроса.
- limit: 1-100, по умолчанию 50. Порядок sort_order ASC, id ASC.
  Ответ: `{items: [...], next_cursor: null | string}`. Пустой список - `[]`.
- Курсор подписан и связан с пользователем, командой, поиском и limit.
  Подмена/изменение параметров даёт 400. Изменения между страницами могут
  менять состав списка; снимок не гарантирован, поиск нужно начать заново.
- Чужая, скрытая и отсутствующая карточки дают одинаковый 404. Неверные UUID,
  неизвестные/повторные параметры - 400; без входа - 401; отказ хранилища - 503.
  Браузер не задаёт team_id, роль и user_id.

Frontend использует UUID и отменяемые запросы. Ключ кэша включает пользователя
и поиск; общий выход очищает кэш. Ошибка API не переключает на фикстуры.
Контакт можно скопировать, отправка сообщений не имитируется. Онлайн-статус,
рождение, карта и рабочие часы не добавляются в API-карточки. Остальные вкладки
«Люди» пока демонстрационные. Полный контракт: [OpenAPI](openapi.yaml).

## Формат seed

Файл: `backend/internal/database/seeds/employees.json`. Он встраивается в
db-init; после изменения нужна пересборка образа. Пример:

```json
{
  "employees": [
    {
      "id": "20000000-0000-4000-8000-000000000001",
      "team_id": "4496e76d-35da-5cf7-a3d5-c9a89d88c5a2",
      "user_id": null,
      "display_name": "Олег Тестовый",
      "short_name": "Олег",
      "job_title": "DevOps-инженер",
      "kind": "colleague",
      "tags": ["мониторинг", "деплой"],
      "ask_about": "Grafana и деплой в тестовое окружение",
      "contact_handle": "@oleg_demo",
      "is_key_contact": true,
      "sort_order": 15,
      "active": true
    }
  ]
}
```

- kind: intern, mentor, lead, hr, colleague.
- Имя до 120 символов, короткое имя до 60, должность до 160. Обязательные
  строки непустые. ask_about до 1000 символов, может быть пустым.
- tags обязателен: 0-12 непустых тем до 60 символов. Go нормализует регистр и
  крайние пробелы; повторы после нормализации запрещены.
- contact_handle: до 120 символов либо null. Только выдуманные контакты.
- active обязателен; sort_order >= 0, по умолчанию 0; is_key_contact по умолчанию
  false. Неизвестные поля запрещены. Всего до 1000 строк и до 1 MiB JSON.
- Существующие UUID команд/пользователей брать из [users.md](users.md).
  Не менять логины, UUID и назначения. Для новых коллег без входа user_id=null.
  Связанный user_id равен id и принадлежит той же команде.
- Новые UUID фиксируются один раз и сохраняются при изменении карточки.

Текущие 8 записей (6 связанных пользователей и 2 коллеги без входа) - минимальная
техническая фикстура, а не полный набор для демонстрации.

## Загрузка и проверки

db-init в одной транзакции применяет миграции, пользователей и сотрудников.
JSON проверяется до вставок; ошибка откатывает подготовку БД. Новый ID
добавляется через ON CONFLICT(id) DO NOTHING. Повтор не создаёт дубли и не
перезаписывает изменения карточек. Удаление строки из JSON не удаляет сотрудника.
Изменение или деактивация уже загруженной записи требует явной миграции данных;
правка JSON сама по себе не обновляет существующий том.

Backend: `go test ./internal/database -run Employee` (нужна отдельная БД через
TEST_DATABASE_URL), `go test ./internal/httpapi -run Employee`.
Frontend: `npm test -- src/entities/colleagues.test.ts src/features/people/RemoteTeamTab.test.tsx`.
Полные проверки приведены в README сервисов.
