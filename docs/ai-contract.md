# Контракт взаимодействия Go API и Python AI-service

**Файл в проекте:** `docs/ai-contract.md`  
**Версия:** `1.0-draft`  
**Статус:** Согласован Go API и AI-service  
**Область:** MVP AI-buddy

Документ сохраняет предложенную архитектуру: HTTP для запуска генерации, Redis Pub/Sub для событий, Go для SSE, сохранения данных и проверки прав. Контракт описывает ожидаемое поведение, а не подтверждает наличие реализации.

## 1. Ответственность сервисов

### Go API

- Авторизует пользователя и проверяет доступ к беседе.
- Загружает актуальные данные пользователя, команды и онбординга.
- Создаёт `request_id`, подписывается на Redis и запускает генерацию.
- Принимает, проверяет и буферизует события, передаёт их клиенту через SSE.
- Сохраняет сообщения, источники, предложения действий и результаты выполнения.
- Проверяет права перед каждым MCP-вызовом и перед подтверждением действия.
- Формирует окончательное состояние запроса, включая ошибки транспорта и таймауты.

### Python AI-service

- Валидирует внутренний HTTP-запрос и запускает генерацию асинхронно.
- Работает с LLM и RAG, публикует события генерации.
- Вызывает MCP-инструменты через Go с привязкой к `request_id`.
- Формирует предложения действий без их автоматического выполнения.
- Соблюдает таймаут и защиту от повторного запуска одного запроса.

Клиент взаимодействует только с Go. Прямой доступ клиента к Python и Redis не предусмотрен.

## 2. Идентификаторы и доверенный контекст

Все идентификаторы передаются как непустые строки:

| Поле | Значение |
|------|----------|
| `request_id` | Одна генерация ответа. Создаётся Go, глобально уникален, например UUID. |
| `conversation_id` | Беседа, объединяющая несколько запросов и ответов. |
| `user_id` | Автор текущего сообщения. |
| `team_id` | Команда пользователя в текущем контексте. |
| `action_id` | Сохранённое в Go предложение действия. Создаётся Go. |

Идентификаторы непрозрачны для получателя. Префиксы из примеров не являются требованием к формату.

Go устанавливает `user_id` по проверенному контексту авторизации. `team_id`, `role` и `stage` берутся из доверенных актуальных данных Go. Наличие этих полей в JWT допустимо, но не заменяет актуальную проверку прав при выполнении инструмента. `stage` не обязан храниться в JWT.

`history` загружается Go из доступной пользователю беседы. Клиент не может самостоятельно назначить роль, команду, историю или идентификатор чужой беседы.

В MVP Go допускает только одну активную генерацию на беседу. Одновременный второй запрос отклоняется Go с `409 GENERATION_IN_PROGRESS`. После завершения или ошибки можно начать следующую генерацию.

## 3. Запуск генерации

### 3.1. Транспорт и порядок операций

Go вызывает внутренний HTTP-эндпоинт Python:

```http
POST /chat
Content-Type: application/json
Authorization: Bearer <AI_SERVICE_TOKEN>
```

Адрес задаётся настройкой Go `AI_SERVICE_URL`. Общий служебный секрет `AI_SERVICE_TOKEN` задаётся обоим сервисам через окружение и не передаётся браузеру. Значения токена, история и строки подключения не записываются в технические логи.

Порядок запуска:

1. Go сохраняет сообщение пользователя и запись генерации со статусом `running`.
2. Go подписывается на Redis-канал `chat:{request_id}`.
3. Go дожидается подтверждения подписки от Redis.
4. Go запускает приём и буферизацию событий независимо от наличия SSE-клиента.
5. Только после этого Go отправляет `POST /chat` в Python.

Общий дедлайн генерации составляет 60 секунд с момента первого HTTP-вызова Python. Дедлайн не продлевается при повторе HTTP-вызова или переподключении браузера.

Таймаут одного HTTP-вызова составляет 5 секунд на соединение и получение ответа целиком. Python возвращает подтверждение, не ожидая ответа LLM. События Redis могут поступить до получения Go ответа `202`.

### 3.2. Тело запроса

```json
{
  "request_id": "req_1234567890_abc",
  "conversation_id": "conv_987654321_xyz",
  "user_id": "intern_anya",
  "team_id": "team_avito_ai",
  "role": "intern",
  "stage": "week_1",
  "timestamp": "2026-11-09T19:35:00Z",
  "timezone": "Europe/Moscow",
  "message": "Как мне оформить отгул на завтра?",
  "history": [
    {
      "role": "user",
      "content": "Привет! Я новая стажёрка."
    },
    {
      "role": "assistant",
      "content": "Привет, Аня! Помогу разобраться с онбордингом."
    }
  ]
}
```

| Поле | Тип и ограничения |
|------|-------------------|
| `request_id`, `conversation_id`, `user_id`, `team_id` | Обязательные непустые строки. |
| `role` | `intern`, `buddy` или `lead`. |
| `stage` | Непустой код этапа, например `week_1`, `week_2`, `weeks_3_4`. Если этап неприменим, `not_applicable`. |
| `timestamp` | Момент первого запуска запроса, RFC 3339 в UTC с суффиксом `Z`. Устанавливается Go. |
| `timezone` | Имя часового пояса IANA, например `Europe/Moscow` или `Asia/Yakutsk`. Устанавливается Go из настроек пользователя/приложения. |
| `message` | Непустое после удаления крайних пробелов сообщение, не более 4 000 символов. |
| `history` | Обязательный массив предыдущих сообщений, допускается `[]`. Текущее `message` в него не включается. |

Относительные даты вычисляются по `timestamp` в указанном `timezone`, а не по локальному часовому поясу контейнера. При неоднозначной дате агент уточняет её у пользователя.

### 3.3. История сообщений

- Допустимые значения `history[].role`: `user`, `assistant`.
- `history[].content` имеет тип `string`.
- Передаются последние завершённые пары сообщений в хронологическом порядке, не более 10 сообщений.
- Общий объём `content` не превышает 20 000 символов.
- Go удаляет самые старые пары целиком до соблюдения обоих ограничений. Если последняя пара не помещается, допустима пустая история.
- Системные инструкции и определения инструментов формирует Python; они не передаются как пользовательская история.

Во всех текстовых ограничениях символ означает Unicode code point: `len(text)` в Python и `utf8.RuneCountInString(text)` в Go. JSON кодируется в UTF-8.

### 3.4. HTTP-ответы Python

Успешное принятие нового запроса:

```http
HTTP/1.1 202 Accepted
Content-Type: application/json
```

```json
{
  "request_id": "req_1234567890_abc",
  "accepted": true,
  "duplicate": false
}
```

`202` подтверждает принятие генерации, но не её успешное завершение и не надёжное хранение задания при падении Python. Сбой после `202` обрабатывается общим дедлайном Go.

| Статус | Условие |
|--------|---------|
| `202` | Новый запрос принят или распознан корректный повтор. |
| `400` | Невалидный JSON, обязательное поле отсутствует, неверный тип или превышен текстовый лимит. |
| `401` | Служебный токен отсутствует или неверен. |
| `409` | `request_id` уже использован с другим содержимым запроса. |
| `503` | Известна временная невозможность принять генерацию, например Redis недоступен. |
| `500` | Непредвиденная ошибка при приёме запроса. |

Формат HTTP-ошибки:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "Поле timezone обязательно."
  }
}
```

Python не публикует события для нового запроса, отклонённого до принятия. Ошибки уже принятой генерации передаются событием `error`.

### 3.5. Повтор HTTP-вызова

Python атомарно регистрирует принятый `request_id` в Redis и хранит запись не менее 10 минут после принятия. Запись содержит отпечаток валидированного тела запроса и состояние генерации; регистрацию выполняют до запуска фоновой задачи.

- Тот же `request_id` с тем же содержимым возвращает `202` с `duplicate: true`.
- Повтор не запускает ещё одну генерацию и не переиздаёт прежние события.
- Тот же `request_id` с другим содержимым возвращает `409 REQUEST_ID_CONFLICT`.
- Отпечаток вычисляется по значениям валидированного запроса, а не по исходным байтам JSON.

Go может повторить HTTP-вызов один раз после сетевой ошибки или таймаута, с тем же телом и `request_id`. Если Go уже получил событие генерации, повтор не нужен. Сам по себе потерянный HTTP-ответ не доказывает, что Python не начал работу: при отсутствии однозначного отказа Go продолжает принимать события до финального события или общего дедлайна.

Повтор пользователем после ошибки создаёт новый `request_id`. Это новая генерация. Ключ идемпотентности действия при повторе подтверждения уже созданного `action_id` при этом не меняется.

## 4. Redis и общая схема событий

Используется Redis Pub/Sub. Python публикует в `chat:{request_id}` одно Redis-сообщение на один JSON-объект. NDJSON и разделение сообщений переносами строки не используются.

```json
{
  "event": "token",
  "request_id": "req_1234567890_abc",
  "seq": 1,
  "data": {
    "text": "Для "
  }
}
```

Обязательные поля:

| Поле | Тип |
|------|-----|
| `event` | Одно из `token`, `tool_call`, `action_proposal`, `done`, `error`. |
| `request_id` | Строка, совпадающая с идентификатором запроса и канала. |
| `seq` | Положительное целое число. Нумерация начинается с 1 и увеличивается на 1 для каждого события данной генерации. |
| `data` | JSON-объект, соответствующий типу события. |

Go проверяет схему, идентификатор и последовательность до обработки. Точный дубликат уже принятого события игнорируется. Пропуск номера, противоречащий дубликат, неверный JSON или неизвестный тип события завершают запрос ошибкой протокола. Неизвестные дополнительные поля известных объектов можно игнорировать.

Python публикует ровно одно финальное событие: `done` либо `error`. После него публикация этой генерации прекращается. Go обрабатывает первое допустимое финальное событие, сохраняет терминальное состояние и игнорирует поздние события.

У Redis Pub/Sub нет операции закрытия канала. После обработки финального события или локального завершения запроса Go отписывается от канала.

## 5. Типы событий

Примеры ниже показывают отдельные форматы событий, а не единую последовательность одной генерации.

### 5.1. `token`

```json
{
  "event": "token",
  "request_id": "req_1234567890_abc",
  "seq": 1,
  "data": {"text": "Для оформления отгула "}
}
```

`text` является непустой порцией текста, не обязательно одним токеном LLM. Текстовые порции объединяются в порядке `seq`.

### 5.2. `tool_call`

```json
{
  "event": "tool_call",
  "request_id": "req_1234567890_abc",
  "seq": 2,
  "data": {
    "tool_name": "knowledge.search",
    "arguments": {"query": "порядок оформления отгула"}
  }
}
```

Это визуальное уведомление о текущем шаге агента. Оно не является командой выполнить инструмент, разрешением на действие или подтверждением его результата.

Фактические MCP-вызовы и их результаты передаются отдельно через Go. Go связывает вызов с сохранённым контекстом `request_id` и проверяет права перед каждым вызовом. Переданный Python идентификатор пользователя или аргумент инструмента не может подменить этот контекст.

Python не обходит Go для вызова корпоративных MCP-инструментов. Внутренние операции RAG в Python сохраняют фильтрацию по разрешённой команде и данным пользователя. Схемы MCP-инструментов, адрес сервера и служебная аутентификация MCP фиксируются отдельно в контракте инструментов; событие `tool_call` их не заменяет.

Аргументы в уведомлении предназначены для Go. Go передаёт в UI только разрешённые поля и не раскрывает служебные токены или чужие данные.

### 5.3. `action_proposal`

Python предлагает действие:

```json
{
  "event": "action_proposal",
  "request_id": "req_1234567890_abc",
  "seq": 3,
  "data": {
    "action_type": "absences.create_request",
    "details": {
      "date": "2026-11-10",
      "type": "отгул"
    }
  }
}
```

Схема `details` определяется контрактом конкретного инструмента. Даты передаются как `YYYY-MM-DD`, типы действий и их параметры проверяются Go.

Порядок обработки:

1. Go проверяет допустимость действия, права пользователя и параметры.
2. Go получает `approver` и другие авторитетные значения из доверенных данных.
3. Go создаёт `action_id` и сохраняет предложение со статусом `proposed`.
4. Сохранение предложения идемпотентно по паре `(request_id, seq)`.
5. Только после сохранения Go передаёт предложение в SSE, дополнив `data` полями `action_id`, `status` и проверенными данными, например `details.approver`.
6. Клиент подтверждает сохранённое действие через `POST /actions/{action_id}/confirm`.
7. Go повторно проверяет актуальные права и состояние, выполняет инструмент с устойчивым ключом идемпотентности и сохраняет результат.

Пример `data` после обработки Go:

```json
{
  "action_id": "act_123",
  "action_type": "absences.create_request",
  "status": "proposed",
  "details": {
    "date": "2026-11-10",
    "type": "отгул",
    "approver": "buddy_ilya"
  }
}
```

Одного `action_proposal` или события `done` недостаточно для выполнения действия. Это относится ко всем операциям с побочным эффектом, включая создание заявки и передачу вопроса наставнику, а не только к удалению данных.

Повтор подтверждения одного `action_id` возвращает сохранённый результат либо текущее состояние выполнения и не создаёт второе действие. Состояния и HTTP-ответы подтверждения описываются в Go API отдельно.

### 5.4. `done`

```json
{
  "event": "done",
  "request_id": "req_1234567890_abc",
  "seq": 4,
  "data": {
    "full_text": "Для оформления отгула на завтра необходимо отправить заявку. Проверь параметры в карточке и подтверди отправку.",
    "sources": [
      {
        "document_id": "doc_kb_001",
        "title": "Порядок оформления отсутствий",
        "section": "Отгулы и отпуска",
        "url": "/docs/kb/absences#leaves"
      }
    ]
  }
}
```

- `full_text` является окончательным текстом ответа, не более 20 000 символов. Он заменяет собранный из `token` текст и не добавляется к нему повторно.
- `sources` обязателен, но может быть пустым массивом. Нельзя добавлять выдуманные источники при пустом результате поиска.
- Каждый источник содержит строковые `document_id`, `title`, `section`, `url`. Отсутствующий раздел обозначается пустой строкой.
- `document_id` относится к доступному пользователю документу. `url` указывает на доступный материал приложения, а не на локальную файловую систему контейнера.
- Go сохраняет финальный текст и источники до передачи клиенту `done`.
- Успешная генерация не означает, что предложенное действие уже подтверждено или выполнено.

### 5.5. `error`

```json
{
  "event": "error",
  "request_id": "req_1234567890_abc",
  "seq": 4,
  "data": {
    "code": "LLM_TIMEOUT",
    "message": "Превышено время ожидания ответа от языковой модели."
  }
}
```

`code` является машинным кодом ошибки. `message` является безопасным сообщением для пользователя без трассировок, секретов и внутренних URL.

Минимальные коды потока:

| Код | Кто формирует | Значение |
|-----|---------------|----------|
| `LLM_TIMEOUT` | Python | Истёк таймаут обращения к модели. |
| `LLM_UNAVAILABLE` | Python | Провайдер модели недоступен. |
| `TOOL_FAILED` | Python | Необработанная ошибка инструмента, из-за которой ответ невозможно завершить. |
| `INTERNAL_ERROR` | Python | Непредвиденная ошибка генерации. |
| `AI_UNAVAILABLE` | Go | Python однозначно отказал в приёме запроса или внутренний вызов не может быть выполнен. |
| `GENERATION_TIMEOUT` | Go | Общий дедлайн 60 секунд истёк без допустимого финального события. |
| `STREAM_INTERRUPTED` | Go | Потеряна подписка Redis во время генерации, восстановление активного потока невозможно. |
| `INVALID_AI_EVENT` | Go | Нарушена схема, идентификатор или последовательность событий. |
| `BUFFER_LIMIT` | Go | Превышен лимит буфера событий. |
| `PERSISTENCE_ERROR` | Go | Не удалось сохранить необходимые данные в БД. |

Отказ инструмента по правам может быть штатным результатом MCP: агент объясняет отказ и завершает ответ через `done`. Он не обязан превращаться в техническую ошибку всего потока.

При локальной ошибке Go создаёт терминальное SSE-событие `error` с `seq = последний принятый seq + 1`, завершает запрос и игнорирует последующие события Python. До передачи клиенту Go сохраняет терминальную ошибку, кроме случая недоступности самой БД: тогда отдаётся `PERSISTENCE_ERROR` и ошибка фиксируется в техническом журнале.

Частично показанный ответ при ошибке не считается завершённым ответом assistant и не включается в последующую `history`. Уже сохранённые предложения действий имеют собственный жизненный цикл и остаются в истории действий; сама ошибка генерации их не выполняет.

## 6. SSE, буфер и переподключение

Go передаёт события через `GET /chat/stream/{request_id}`. Перед подпиской и повторным подключением Go проверяет доступ пользователя к соответствующей беседе и запросу.

Пример кадра SSE:

```text
id: req_1234567890_abc:1
event: token
data: {"event":"token","request_id":"req_1234567890_abc","seq":1,"data":{"text":"Для "}}

```

В поле SSE `data` передаётся полный JSON-конверт события. Для `action_proposal` он уже дополнен Go сохранённым `action_id` и проверенными полями. Имя SSE `event` совпадает с JSON-полем `event`.

- Go использует `Content-Type: text/event-stream` и сбрасывает буфер HTTP после отправки события.
- Пока генерация активна, Go может отправлять комментарий `: ping` каждые 15 секунд. Комментарии не имеют `seq`.
- Клиент передаёт `Last-Event-ID` при переподключении. Go воспроизводит сохранённые события с большим `seq`. Идентификатор другого запроса отклоняется.
- Если `Last-Event-ID` отсутствует, Go воспроизводит доступные события с начала запроса.
- Фронтенд игнорирует повторно полученные события с уже обработанным `seq`.
- Go хранит буфер в памяти процесса во время генерации и 10 минут после её завершения, максимум 4 MiB JSON-событий на запрос. При превышении лимита запрос завершается через `BUFFER_LIMIT`.
- После удаления буфера терминальный запрос восстанавливается из БД: Go передаёт сохранённые `action_proposal` и терминальное событие с исходными номерами. Предыдущие `token` и `tool_call` восстанавливать не требуется; `done.full_text` восстанавливает текст целиком.
- Если буфер незавершённой генерации потерян, например после перезапуска Go, запрос завершается через `STREAM_INTERRUPTED`. Прозрачное продолжение такой генерации в MVP не гарантируется.

Закрытие вкладки, разрыв сети или отключение SSE не отменяют генерацию. Go продолжает принимать события и сохранять результат независимо от браузерного подключения. Переподключение не вызывает новый `POST /chat`.

Отдельная пользовательская отмена генерации в MVP не реализуется. Python ограничивает собственную работу таймаутом не более 60 секунд; Go независимо обеспечивает общий дедлайн. После локальной ошибки Go Python может завершать уже начатую работу до своего таймаута, но её поздние события не применяются.

## 7. Ограничения Redis Pub/Sub

Pub/Sub не хранит события и не обеспечивает их повторное получение после потери подписки. Наличие `seq` помогает обнаружить нарушение последовательности, но не восстанавливает потерянные сообщения.

Поэтому для MVP обязательны:

- Подписка Go до запуска Python.
- Приём событий вне жизненного цикла SSE-соединения.
- Буферизация в Go и сохранение результатов в БД.
- Явная ошибка при потере активной Redis-подписки.
- Общий дедлайн на случай потери финального события или падения Python.

Сохранение Redis AOF не превращает Pub/Sub в надёжную очередь событий. Redis Streams можно рассмотреть позже при необходимости восстановления незавершённых потоков после перезапуска Go; для согласованного MVP переход на Streams не требуется.

## 8. Минимальные приёмочные проверки

1. Обычный запрос: Python возвращает `202`, Go получает события с `seq` от 1, клиент видит текст, Go сохраняет `done.full_text` и источники.
2. Очень быстрый ответ: Python публикует событие до получения Go ответа `202`; событие не теряется.
3. Позднее подключение SSE: события, пришедшие до браузерной подписки, воспроизводятся из буфера.
4. Переподключение SSE: уже показанные события не дублируются, новая генерация не запускается.
5. Повтор HTTP-запроса с тем же `request_id`: запускается одна генерация; изменённое тело с тем же ID получает `409`.
6. Потеря ответа `202`: Go не объявляет генерацию несуществующей, продолжает принимать её события в пределах исходного дедлайна.
7. Запрос чужой беседы, SSE чужого запроса и запрещённый MCP-вызов отклоняются Go.
8. `action_proposal` создаёт одну сохранённую карточку; без подтверждения действие не выполняется, повтор подтверждения не создаёт дубль.
9. Потеря Redis-подписки, неверное событие и пропуск `seq` дают терминальную ошибку, поздние события игнорируются.
10. Отсутствие финального события завершает запрос через 60 секунд; после `done` или `error` запрос не меняет терминальное состояние.
11. Обрыв SSE не отменяет генерацию; после её завершения ответ доступен из истории.
12. Сохранение `done` или предложения действия завершается ошибкой БД: клиент не получает ложное подтверждение успешного сохранения.

## 9. Границы этого документа

Отдельно согласовываются схемы MCP-инструментов и их результатов, служебная аутентификация MCP, схема таблиц, HTTP-контракт подтверждения действий и внешний API создания сообщений. Они должны сохранять описанные здесь идентификаторы, проверку прав и идемпотентность.

Изменения типов полей, семантики событий и правил завершения согласовываются обеими сторонами до реализации. Добавление необязательного поля совместимо с этой версией, если существующее поведение сохраняется.
