# Работа над AI-buddy

Одна фича или исправление выполняется в отдельной ветке. Для агента можно использовать отдельный чат на задачу: необходимые договорённости должны находиться в issue и документах репозитория, а не только в переписке.

## Перед началом задачи

1. Прочитать `AGENTS.md`, описание задачи и только связанные разделы документации из README.
2. Проверить ветку и `git status`. Чужие изменения не перезаписывать и не включать в свой коммит.
3. Обновить сведения об `origin/main` и создать ветку `feat/...`, `fix/...`, `docs/...`, `test/...`, `chore/...` или `ci/...`. Зависимость от открытого PR и другую базовую ветку указать явно. Не сливать чужой PR без запроса.
4. Для задачи на доске указать issue, назначить исполнителя, перевести карточку в `In progress`. Если issue не указан, найти подходящий, не связывать PR с посторонней задачей.
5. Зафиксировать ожидаемый результат и границы. Если пользователь запросил одобрение плана, дождаться его до редактирования.

Пример начала вручную:

```bash
git status --short
git fetch origin
git switch -c feat/my-task origin/main
```

## Шаблон запроса для нового чата

```text
Реализуй issue #N: <краткое название>.
Создай отдельную ветку от актуального main. Следуй AGENTS.md.

Ожидаемый результат: <что должно работать и как проверить>.
Границы: <какие части менять; чего задача не включает>.
Зависимости: <связанные PR/контракты или «нет»>.

Сначала опиши короткий план и дождись моего одобрения.
После реализации выполни подходящие проверки, создай коммит и PR в main.
В описании PR укажи Closes #N, проверки и известные ограничения.
```

Без обязательного одобрения удалите строку про ожидание. Если push и PR не нужны, замените последнюю часть на «сделай изменения локально, не отправляй ветку и не создавай PR».

При продолжении укажите ветку, issue/PR и оставшийся результат. Не переносите весь старый чат: сначала сохраните важные решения в относящемся к ним документе.

## Проверки по типу изменения

| Изменение | Начальные проверки |
|-----------|--------------------|
| Go-код | Форматирование, тесты затронутого модуля, go vet и golangci-lint. Команды: [backend/README.md](backend/README.md#проверки). Для конкурентного поведения при доступном toolchain уместен race detector. |
| Compose/Dockerfile | `docker compose config --quiet`, сборка и запуск затронутого сервиса с зависимостями, рабочий endpoint и журналы. При изменении остановки проверить завершение контейнера. |
| Только Markdown | Ссылки, актуальность статусов, согласованность с источниками/контрактом, JSON-примеры при наличии, diff и тире. Go-тесты и пересборка Docker без причины не нужны. |
| API-контракт или БД | Помимо формата проверить совместимость и связанные сценарии. Документ схемы не считается выполненной SQL-миграцией. |
| Frontend/Python | Использовать команды из конфигурации и README сервиса, когда они появятся в ветке. Не выдумывать отсутствующие scripts, инструменты и результаты. |

Успешную проверку повторяют после относящихся к ней изменений или при новом основании. Нужны проверки поведения, включая ошибки и права, а не тесты, повторяющие реализацию.

После добавления файлов в индекс:

```bash
git diff --cached --check
git grep --cached -nP '[\x{2013}\x{2014}]' -- . ':!*.lock'
```

У `git grep` ожидается пустой вывод и код 1. Остальные коды и совпадения требуют разбора. Для Markdown, включая ещё не добавленные файлы, можно использовать `rg -n '[\x{2013}\x{2014}]' -g '*.md'`.

## Коммит и PR

- `main` защищён: изменения проходят через PR и ревью другого участника.
- Коммит: `тип: описание`, например `feat: добавить GET /health`. Типы перечислены в AGENTS.md.
- Коммит содержит только проверенные файлы задачи. Используется настроенный Git-автор пользователя без атрибуции агентам.
- Push и PR агентом требуют явного запроса. Шаблон выше уже разрешает оба действия; повторное одобрение тех же действий не нужно.
- PR описывает итог, проверки и ограничения. Для полностью закрываемого issue используется `Closes #N`, для частичной работы или зависимости - `Связано с #N`.
- Если подходящий issue не найден, не подставляйте произвольный номер. Укажите это при передаче результата; при необходимости согласуйте создание issue.
- Открытый PR не является готовой функцией в `main`. Изменение рабочего запуска, готовности сервиса или пути документа отражается в README в том же PR.

## Передача результата следующему чату

В итоге достаточно указать результат и оставшуюся работу, изменённые файлы, выполненные проверки и ограничения, ветку, коммит и PR, если они созданы.

Решения по требованиям, контракту и схеме сохраняются в соответствующем документе. Не создавайте дублирующие файлы статусов, дневники каждого шага и новые спецификации для маленькой правки. Существующие документы других задач без необходимости не меняйте. Если зависимость ещё в PR, укажите ссылку и её статус.

После слияния следующую независимую задачу начинайте от обновлённого `main`. Спорные продуктовые решения согласуются в командном чате или issue и затем фиксируются в документах.
