# Go API

API на Go 1.27. Подготовка PostgreSQL использует pgx v5.

## Локальный запуск

Из каталога `backend`:

Сначала подготовьте БД по инструкции ниже и задайте `DATABASE_URL`,
`JWT_SIGNING_KEY` и при необходимости `JWT_TTL` в окружении процесса.

```bash
go run ./cmd/api
```

Проверка из другого терминала:

```bash
curl -i http://localhost:8080/health
```

Ожидаются HTTP 200, `Content-Type: application/json` и `{"status":"ok"}`.
`POST /health` возвращает 405, неизвестные пути возвращают 404.
Остановка: Ctrl+C или SIGTERM, до 10 секунд на завершение активных запросов.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
|------------|----------------------|------------|
| `HOST` | `0.0.0.0` | Адрес прослушивания, поддерживается IPv6 |
| `PORT` | `8080` | Порт от 1 до 65535 |
| `LOG_LEVEL` | `INFO` | Уровень JSON-логов: DEBUG, INFO, WARN, ERROR |
| `DATABASE_URL` | обязательно | Строка подключения PostgreSQL для пользователей |
| `REDIS_URL` | пусто | Redis Pub/Sub; обязателен для чата |
| `AI_SERVICE_URL` | пусто | Внутренний HTTP-адрес Python без пути `/chat` |
| `AI_SERVICE_TOKEN` | пусто | Общий сервисный Bearer-токен Go/Python |
| `JWT_SIGNING_KEY` | обязательно | Ключ HS256, минимум 32 байта; не записывается в логи |
| `JWT_TTL` | `1h` | Срок JWT от 1s до 24h, целое число секунд |

Приложение читает окружение процесса. `.env` автоматически читает только Docker Compose.
API проверяет соединение с PostgreSQL при запуске. Если заданы AI_SERVICE_URL
и AI_SERVICE_TOKEN, подключает чат через Redis. Если оба отсутствуют, маршруты
чата выключены; частичная конфигурация считается ошибкой.
`/health` проверяет только работу HTTP-сервера, не текущее состояние БД.
Ошибки настройки и запуска завершают процесс с кодом 1. URL подключений в логи не пишутся.

## Docker

Из корня репозитория, после создания `.env` по примеру:

```bash
docker compose up --build -d backend
curl -i http://localhost:8080/health
docker compose logs backend
```

Compose также поднимет PostgreSQL и Redis. Frontend и AI-сервис не нужны для проверки API.
Dockerfile собирает статический бинарник, запускает его без прав root и устанавливает CA-сертификаты.

Из каталога `backend` (golangci-lint v2):

```bash
go test '-coverprofile=coverage.out' ./...
go tool cover '-func=coverage.out'
go vet ./...
golangci-lint run
```

## Структура

- `cmd/api`: точка входа, сигналы завершения, сборка зависимостей.
- `internal/config`: чтение и проверка env.
- `internal/httpapi`: маршруты и логирование запросов.
- `internal/server`: HTTP-сервер и корректное завершение.

Маршруты создаются в `cmd/api` и передаются в сервер через `http.Handler`.
Compose даёт backend 15 секунд на остановку, включая 10 секунд на завершение
активных HTTP-запросов. После таймаута соединения закрываются принудительно.

## Подготовка БД и пользователи

Из каталога backend, перед локальным запуском API:

```powershell
$env:DATABASE_URL = "postgres://ai_buddy:ai_buddy_dev@localhost:5432/ai_buddy?sslmode=disable"
go run ./cmd/db-init
```

В Compose сервис `db-init` выполняет эту команду после готовности PostgreSQL.
Backend запускается после успешного завершения `db-init`. Ошибка подготовки
блокирует запуск backend. HTTP-процесс DDL не выполняет. Явный повторный запуск:
`docker compose run --rm db-init`.

Healthcheck PostgreSQL проверяет TCP, чтобы временный Unix-сервер первичной
инициализации не считался готовым для подключения из `db-init`.
На первый initdb отведен start_period 60 секунд перед учетом неудачных проверок;
успешный TCP-healthcheck может завершить ожидание раньше.

SQL встроен в бинарник: `internal/database/migrations/*.sql` и
`internal/database/seeds/users.sql`. Чек-лист читается из единственного
`seed/checklist.json` в корне репозитория. При локальном запуске db-init из backend
путь по умолчанию `../seed/checklist.json`; переопределение - `CHECKLIST_SEED_PATH`.
В Compose каталог seed монтируется в db-init только для чтения, путь задан явно.
Отсутствующий или некорректный JSON блокирует подготовку, а не пропускается.
Миграции применяются по имени файла,
учитываются в `schema_migrations` с SHA-256. Переносы строк нормализуются к LF;
сохраненные прежней версией суммы CRLF также принимаются для того же содержимого.
Изменение SQL по-прежнему блокирует запуск. Применённые файлы не редактируются:
для изменения схемы добавляйте следующий номер. Неизвестная применённая миграция
блокирует запуск старого инициализатора. Автоматического отката схемы нет;
исправления выполняются новой миграцией.

Миграции и seed выполняются одной транзакцией с advisory lock. Создаются
`teams`, `users`, `onboarding_plans`, `tasks`, `task_status_history`: 2 команды,
6 пользователей, 2 плана и 30 задач. Каждая новая задача получает одну начальную
запись истории версии 1. Примененная `0001_users.sql` не изменена; онбординг
добавлен через `0002_onboarding.sql` и работает на существующем томе.

Повторный seed добавляет отсутствующие записи по UUID, не меняя существующие
имена, активность, команды, назначения, архивные планы, статусы, версии и сроки
задач. Новая задача проверяет принадлежность исполнителя владельцу плана или
назначенному наставнику. Коллизия логина, владельца плана или seed_key с другим
объектом является ошибкой, а не поводом изменить чужую запись.
Роли назначенных пользователей и циклы руководителей проверяет прикладной слой
при будущей реализации изменения назначений. Seed содержит корректные назначения.

UUID команд и пользователей в JSON и docs/users.md совпадают с уже применяемым
SQL seed. UUID планов, задач и документов Саши сохранены. Seed не меняет первичные
ключи и не требует удаления данных или тома.

26 связей `task_kb_documents` сохранены в JSON и проверяются на корректность ID,
команд, позиций и ссылок на задачи, но пока не записываются в БД. Таблицы KB и
реальные документы еще не загружаются: зависимость от #28 и PR #56/#69.
Инициализатор сообщает об отложенных связях. Фиктивные документы не создаются.
После KB-интеграции нужны отдельная миграция связей с FK и их загрузка; повторяемый
seed пользователей и задач по критерию #19 уже не зависит от этой интеграции.

Интеграционные тесты используют отдельные временные схемы в тестовой БД:

```powershell
$env:TEST_DATABASE_URL = "postgres://postgres:synthetic_test@localhost:55439/ai_buddy_test?sslmode=disable"
go test ./...
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. В CI PostgreSQL
поднимается автоматически, эти тесты обязательны. Тестовой учётной записи нужны
права создания и удаления собственных схем. Рабочую БД для тестов не используйте.

## Мок-авторизация

Мок-вход предназначен для синтетического демо и не проверяет личность пользователя.
`POST /auth/mock-login` принимает `Content-Type: application/json` и
`{"login":"intern_anya"}`. Роль, UUID и команда выбираются из PostgreSQL.
Лишние поля и некорректный JSON дают 400, неизвестный или неактивный пользователь
либо команда дают 401. Ошибка доступа к БД даёт безопасный ответ 503.

Ответ 200 содержит `access_token`, `token_type: Bearer`, `expires_in` и `user`.
JWT подписан HS256 и содержит `sub`, `user_id`, `role`, `team_id`, `iat`, `exp`,
фиксированные issuer `ai-buddy` и audience `ai-buddy-web`. `sub = user_id`.
Секрет из `.env.example` синтетический и годится только для локального запуска;
при совместном развёртывании задайте собственный ключ. Старый `.env` нужно дополнить
`JWT_SIGNING_KEY` и `JWT_TTL`. Ключ пользователя не связан с `AI_SERVICE_TOKEN`.

`GET /me` защищён `RequireAuth` и возвращает текущий профиль. Заголовок запроса:
`Authorization: Bearer <access_token>`. Без токена, с испорченным/просроченным JWT
или после деактивации пользователя/команды возвращается 401. `/health` и вход
публичны. Смена ключа подписи делает прежние токены недействительными.

Middleware повторно читает пользователя из БД; роль и команда токена не заменяют
актуальный профиль. Контекст текущего пользователя доступен через `CurrentUser`.
Новые прикладные маршруты должны использовать `RequireAuth`; проверки владельца,
назначения наставника и прав конкретной операции выполняются через `internal/policy`.
Токены не передаются в URL и не записываются в логи. Ответы авторизации не кешируются.

## Policy-слой

`internal/policy.Check` получает актуального пользователя и доверенные атрибуты
ресурса. Проверяет роль, совпадение team_id, владельца, назначение наставника и
исполнителя задачи. Неизвестная роль или операция запрещена. Пустой код причины
означает разрешение. Пакет не читает JWT, аргументы агента или БД самостоятельно.

Подключены `checklist.get_plan`, `checklist.update_status`, `chat.create` и
`chat.read` (история и получение генерации для SSE). Это внутренние имена проверок,
а не реализованный MCP-сервер. Перед проверкой Go загружает активного пользователя
активной команды из БД; SQL также ограничивает выборку областью доступа.

Матрица доступа сохраняет правила API: intern читает свой план, buddy - планы
назначенных стажеров, lead - планы своей команды. Статус меняет только исполнитель
в доступном плане. Беседы и генерации доступны только владельцу для всех трех ролей.
Новые инструменты должны явно добавить собственное правило до подключения.

При отказе основная транзакция откатывается, затем отдельная запись в `events`
сохраняет `event_type=policy_denied`, команду и ID инициатора. Payload версии 1
содержит только `operation` и безопасный `reason`. ID запрошенного объекта, тексты
переписки и чужие FK не записываются. Недоступный и отсутствующий объект одинаково
дают 404 и `reason=resource_unavailable`, без дополнительного поиска чужого объекта.
Поэтому это событие означает отказ в выдаче ресурса, а не доказанную атаку.
Видимая задача другого исполнителя по-прежнему дает 403 `POLICY_DENIED`.

Запись отказа имеет отдельный таймаут 5 секунд и сохраняется также при отмене
HTTP-запроса. При ошибке аудита операция остается запрещенной, клиент получает
503 вместо обычного ответа отказа. 400, 401, конфликт версии и неактивный план
не считаются отказами policy. Существующая таблица events не требует новой миграции.

HTTP-схемы соответствуют черновику [PR #68](https://github.com/ai-buddy-hc2026/ai-buddy/pull/68).
Общий OpenAPI остается черновиком. В этой ветке реализованы `/me` и операции
онбординга #21 ниже; база ветки - миграции/seed #78 и авторизация #77.

## API онбординга

Оба endpoint требуют `Authorization: Bearer <access_token>`.

- `GET /onboarding/plan`: стажер читает свой активный план. Buddy/lead передают
  `?intern_id=<uuid>`; buddy видит назначенных стажеров, lead - свою команду.
  Возвращаются три этапа с массивами tasks, общий progress и next_task_id.
- `PATCH /tasks/{id}` принимает только `{"status":"done","version":1}`.
  Исполнитель меняет свою задачу в доступном активном плане. Видимая задача
  другого исполнителя дает 403 POLICY_DENIED; недоступный/отсутствующий объект
  дает одинаковый 404. Архивный/завершенный план дает 409 PLAN_NOT_ACTIVE.
- Изменение увеличивает version на 1 и атомарно сохраняет task_status_history
  и events.task_status_changed. Устаревшая version дает 409 VERSION_CONFLICT.
  Тот же status с актуальной version возвращает задачу без новой истории/события.
- Следующая задача - первая не в done по этапу, позиции и ID, включая blocked
  и задачи наставника. При пустом/завершенном наборе next_task_id=null;
  percent пустого плана равен 0. current_stage и статус плана автоматически
  не меняются. Это согласованное правило для #21.
- Пока KB не загружена, materials каждой задачи - пустой массив. Не используются
  выдуманные ссылки из незагруженных связей. Интеграция frontend остается отдельной.

Миграция 0003 создает events для транзакционной записи task_status_changed.
Миграция 0004 добавляет conversations, chat_requests и chat_messages, снимает
временное ограничение events.request_id и добавляет составной FK по команде.
events.action_id по-прежнему ограничен NULL до реализации действий.
История и события генезиса seed не смешиваются: после чистого db-init
task_status_history содержит 30 записей, events пуста.

## Чат и SSE (#24)

Все маршруты требуют JWT в `Authorization: Bearer <token>`. Доступ есть только
к своим беседам; чужой и отсутствующий UUID дают одинаковый 404.

- `POST /chat/messages`: `{\"message\":\"Вопрос\",\"conversation_id\":\"<uuid>\"}`.
  conversation_id необязателен: выбирается или создается активная беседа.
  Ответ 202 содержит request_id, conversation_id, status и stream_url.
  Одновременно разрешена одна генерация на беседу, иначе 409.
- `GET /chat/stream/{request_id}`: SSE token/done/error. `id` каждого события
  равен `<request_id>:<seq>`, data содержит весь JSON-конверт StreamEvent.
  Комментарий `: ping` отправляется каждые 15 секунд. Для проверки используйте
  `curl -N -H "Authorization: Bearer <token>" <stream_url>` с полным URL.
- `Last-Event-ID: <request_id>:<seq>` восстанавливает события после курсора.
  Неверный или будущий курсор дает 400 до открытия потока. Буфер до 4 MiB
  хранится в памяти процесса во время генерации и 10 минут после завершения.
- `GET /chat/messages?conversation_id=<uuid>&limit=50&cursor=<next_cursor>`:
  страницы запросов от старых к новым, user/assistant, состояние и next_cursor.
  Без conversation_id выбирается активная беседа. active_request возвращается
  независимо от страницы. actions пока всегда пуст; limit от 1 до 100.

Go подтверждает Redis-подписку до POST /chat в Python. Дедлайн генерации -
60 секунд, вызов запуска - до 5 секунд. Один повтор неопределенного запуска
использует неизменный payload/request_id; Python защищает запуск через SET NX.
Повтор браузерного POST после потери ответа делать автоматически нельзя:
сначала восстановите историю и active_request.

Отключение браузера не отменяет генерацию. Go сохраняет итог в PostgreSQL
перед отправкой done, вместе с answer_completed; вопрос и chat_question
сохраняются вместе при принятии. Частичный assistant при ошибке не сохраняется.
Ошибка сохранения становится PERSISTENCE_ERROR; ошибка подписки/разрыв Redis -
STREAM_INTERRUPTED, превышение размера - BUFFER_LIMIT. Технические детали
Python/БД не передаются клиенту. full_text в done заменяет частичный текст.

Профиль #24 поддерживает token/done/error и пустые sources. MCP/tool_call,
action_proposal и проверка доступа к RAG-источникам относятся к #43/#44/#28.
Такие события сейчас завершают запрос INVALID_AI_EVENT без выполнения действий.
Это реализация транспортного профиля, а не всего черновика контракта.

MVP рассчитан на один процесс Go. После потери буфера завершенный итог
восстанавливается из PostgreSQL с исходным терминальным seq. Активные запросы
при старте Go становятся STREAM_INTERRUPTED. Если Last-Event-ID больше
восстановленного seq, получите историю без курсора: прозрачное продолжение
потерянной генерации через Pub/Sub не поддерживается.

Для Go-интеграционных тестов задайте TEST_DATABASE_URL и TEST_REDIS_URL
на отдельные PostgreSQL/Redis; затем выполните `go test -race ./...`.
Тест разрыва Redis закрывает только свою именованную тестовую подписку.
Без переменных соответствующие тесты пропускаются.

Воспроизводимая проверка настоящего Python и Redis без внешней LLM из корня:

```bash
docker compose -f docker-compose.yml -f compose.test.yml up --build -d --wait backend ai-service mock-llm
python tests/chat_sse_smoke.py
docker compose -f docker-compose.yml -f compose.test.yml down
```

compose.test.yml подменяет только провайдера Python синтетическим
OpenAI-совместимым сервером. Для обычного чата настройте провайдер в .env;
для локальной Ollama запустите Compose с `--profile ollama` и дождитесь загрузки
модели. ai-service использует имя `ai-service`, а не прежнее `ai-servise`.
Frontend подключается к SSE через fetch с заголовком Authorization;
интеграция UI и CORS остается отдельной задачей.
