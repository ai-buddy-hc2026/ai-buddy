# Правила для агентов

## Контекст проекта

AI-buddy - помощник стажёра для Hack&Change 2026. Go отвечает за внешний API, авторизацию, права и выполнение действий; Python за агента, LLM и RAG; React + TypeScript за интерфейс.

- Начинай с описания задачи, git status и затронутых файлов. Состояние реализации и карта документов находятся в README.md.
- Для границ фичи используй нужный сценарий в docs/mvp.md; docs/requirements/case.md читай при вопросах к исходным требованиям.
- При изменении протокола читай соответствующий контракт, для БД - docs/db.md, если он уже есть в ветке. Пока документа нет в main, проверь ссылку на его PR в README и укажи зависимость.
- Детали запуска и проверок Go: backend/README.md; процесс и шаблон нового чата: CONTRIBUTING.md.
- Не читай весь репозиторий, PDF и все спецификации перед каждой задачей. Загружай относящиеся к изменению документы; не повторяй чтение неизменившихся файлов без причины.

## Работа и границы

- Сохраняй принятые решения в соответствующем документе, чтобы следующий чат не зависел от переписки. Не создавай журнал на каждую маленькую правку.
- Не меняй межсервисный контракт, область доступа или состав MVP молча. Изменение вне уже одобренной задачи сначала согласуй.
- Если пользователь запросил план с одобрением, не редактируй файлы до одобрения. Одобренный план выполняй без повторных вопросов о тех же действиях.
- Не объявляй черновик согласованным, открытый PR влитым, а запланированную возможность реализованной.
- В приложении права проверяются в Go перед каждым инструментом. Действия с побочным эффектом требуют подтверждения пользователя в UI и устойчивого ключа идемпотентности. Промпт не заменяет авторизацию.
- Используй синтетические данные. Не добавляй секреты и реальные данные сотрудников в Git.

## Git

- Сначала проверь незакоммиченные изменения. Не перезаписывай, не добавляй в индекс и не коммить чужие изменения.
- Для задачи создавай отдельную ветку от актуального main, если пользователь не указал другую базу. Зависимость от открытого PR обозначай явно.
- Не используй force-push или git reset --hard. Не удаляй незакоммиченные изменения без разрешения.
- Локальный коммит допустим после проверок. Push и PR выполняй только по явному запросу пользователя.
- Используй настроенные user.name и user.email, не меняй их. Не добавляй агентов/модели в авторы и co-authors, не добавляй атрибуцию ИИ в сообщения коммитов и описания PR.
- Коммиты: `тип: описание`, типы feat, fix, docs, test, chore, refactor, ci. Описание для команды пиши по-русски.

## Проверки и экономия контекста

- Выбирай проверки по изменению: Go - тесты и линтер затронутого модуля; Compose - конфигурация и затронутые сервисы; документы - ссылки, формат и согласованность. Команды находятся в README модуля и CONTRIBUTING.
- Повторяй успешные проверки после новых изменений или при конкретной причине, а не по кругу.
- Поиск начинай с rg; ограничивай область и вывод. Длинные процессы ожидай с разумными интервалами, не опрашивай каждые несколько секунд без причины.
- Выводи полезный итог и ошибки, а не весь журнал. Не включай секреты в вывод.
- В конце сообщи результат, файлы, выполненные проверки, ограничения и коммит/PR, если они созданы.

## Язык и тире

Документы и тексты для команды пиши на русском, простым языком. Используй только дефис `-`, включая диапазоны 3-4 недели и 50-100 символов. U+2013 и U+2014 запрещены в коде, комментариях, документах, коммитах, PR и issues. В редактируемых строках заменяй существующие запрещённые тире.

После добавления файлов в индекс, перед коммитом:

```bash
git diff --cached --check
git grep --cached -nP '[\x{2013}\x{2014}]' -- . ':!*.lock'
```

Последняя команда не должна ничего найти; код 1 у git grep означает отсутствие совпадений. Проверка индекса включает новые добавленные файлы.
